# 阶段一：测试基础

## 第三章：缺陷管理

> 本章目标：能够判断什么是缺陷，准确描述、提交、跟踪和关闭缺陷，并能使用 Excel 或禅道完成缺陷管理；最终可以把一次测试执行转化为规范、可复现、可协作的缺陷记录。

## 一、本章能力地图

| 能力 | 学完后的可交付结果 |
| --- | --- |
| 缺陷识别 | 能从需求、设计、代码、环境和实际使用结果中识别缺陷 |
| 缺陷判断 | 能区分少功能、多功能、错误功能、隐性功能错误和易用性问题 |
| 缺陷分级 | 能分别判断严重程度（Severity）和修复优先级（Priority） |
| 缺陷编写 | 能写出标题清晰、步骤完整、预期和实际可对照的缺陷报告 |
| 缺陷协作 | 能处理新建、确认、修复、重测、关闭、拒绝、延期和重新打开等状态 |
| 工具使用 | 能在 Excel、禅道等工具中维护用例、提交缺陷和查看统计 |
| 就业实践 | 能针对注册、登录、QQ、电话、文件、ATM 等场景提交完整缺陷 |

## 二、课程视频主线

第三章视频按照“执行用例 → 认识缺陷 → 编写缺陷 → 工具管理 → 案例练习”的顺序展开：

3. **3-3 缺陷编写**：缺陷格式与练习、缺陷评审和标题描述、缺陷流程。

# 3-1 认识缺陷

## 3-1.1 从执行用例开始发现缺陷

测试人员不是“看到页面不顺眼就提 Bug”，而是按照测试用例执行操作，将**实际结果**与**预期结果**进行比较。

一次完整的发现过程通常包括：

1. 阅读需求或测试用例，明确业务规则。
2. 准备前置条件、账号、数据和测试环境。
3. 严格按照步骤执行，避免因为操作顺序错误产生假缺陷。
4. 记录实际结果、时间、环境、账号、数据和日志。
5. 重复执行，判断问题是否可稳定复现。
6. 对照需求、原型、接口约定或历史版本，确认预期结果。
7. 判断这是缺陷、需求变更、环境问题、数据问题还是操作问题。
8. 通过缺陷管理工具提交并跟踪。

### 执行用例时的证据意识

缺陷发现阶段就要开始留证据，不要等开发追问时再回忆。建议保留：

- 测试环境地址、版本号、浏览器和设备信息；
- 测试账号、角色、租户或权限信息（敏感信息脱敏）；
- 关键输入数据和接口请求参数；
- 页面截图、录屏、控制台日志、网络请求、服务端日志；
- 发生时间和时区；
- 关联用例编号、需求编号、任务编号。

## 3-1.2 什么是软件缺陷

课程中的定义是：**软件在使用过程中存在的任何问题，都可以称为软件缺陷，简称 Bug。**

在企业中，更严谨的表达是：

> 软件的实际行为与需求、设计、接口契约、行业规则、法律法规、用户合理预期或产品质量标准不一致，并且这种不一致会造成错误、风险、损失或明显的使用障碍，就可以作为缺陷进行评估。

缺陷不只存在于代码中，也可能存在于：

- 需求文档和验收标准；
- 产品原型、交互设计和视觉设计；
- 数据库结构、初始化数据和配置；
- 部署脚本、环境变量和第三方依赖；
- 接口协议、权限模型和安全控制；
- 帮助文档、提示语、报表和运营配置。

## 3-1.3 缺陷判定的五类标准

课程将缺陷判定归纳为五类。实际工作中应先确认需求和验收口径，再使用下面的分类。

### 1. 少功能

需求明确要求的功能没有实现，或关键分支缺失。

例：需求要求注册成功后自动登录，实际注册成功后既没有登录，也没有明确提示下一步。

### 2. 功能错误

软件实现了功能，但结果、规则或处理逻辑与需求不一致。

例：QQ 账号要求 6～10 位自然数，输入 4 位数字却被判定为合法；优惠券金额为 0 时仍被当作有效优惠券使用。

### 3. 多功能

软件实现了需求没有要求、且可能改变业务行为的功能。多功能不等于“功能丰富”，如果未经需求确认就增加行为，可能造成权限、合规或数据风险。

例：普通用户页面出现管理员删除按钮；提交订单时系统自动修改用户收货地址，而需求没有授权此行为。

### 4. 隐性功能错误

需求没有逐字写出，但根据业务常识、行业规则、法律法规、平台约定或用户合理预期，软件应当具备而没有具备的能力。

例：密码输入框明文显示；注销后旧 Token 仍能访问个人数据；支付成功但订单状态没有更新；注册接口没有限制重复手机号。

### 5. 易用性或非功能问题

功能表面上可以完成，但存在难以理解、不易操作、响应过慢、兼容性差、可访问性差或用户体验明显不合理的问题。

例：错误提示只显示“系统异常”，没有说明如何修正；移动端按钮被键盘遮挡；页面在支持的浏览器中错位；大批量查询导致接口长期无响应。

## 3-1.4 缺陷、需求变更和咨询问题的区别

| 情况 | 是否直接提 Bug | 处理建议 |
| --- | --- | --- |
| 实际结果违反已确认需求 | 是 | 提交缺陷并关联需求 |
| 需求没有规定，产品希望新增能力 | 通常不是 | 提交需求变更或产品任务 |
| 测试人员不了解规则，无法判断预期 | 暂不提交 | 先向产品或业务确认，并保留确认结论 |
| 测试环境服务未启动 | 通常不是产品 Bug | 提交环境问题或通知运维 |
| 测试数据失效导致结果异常 | 先排除数据问题 | 补充数据后复测，必要时提交数据问题 |
| 同一问题已经存在 | 不重复提交 | 关联原缺陷，补充新的影响范围 |

## 3-1.5 缺陷产生的原因

课件将缺陷来源分为四个阶段。测试人员提交的是“发现的问题”，不一定要在提交时准确判断根因；根因分析通常由开发、架构或项目团队共同完成。

### 需求阶段

- 需求描述不清晰、有歧义；
- 正常、异常和边界规则没有写全；
- 角色、权限、状态和异常流程遗漏；
- 需求与原型、接口文档、历史规则不一致；
- 验收标准无法验证，例如“页面要快”“体验要好”。

### 设计阶段

- 数据库字段、索引、约束设计错误；
- 接口协议、错误码或幂等规则设计不完整；
- 状态机缺少某些状态转移；
- 权限模型只设计了正常流程，没有设计越权场景；
- 兼容性、容量和降级方案未考虑。

### 编码阶段

- 条件判断、循环、类型转换、空值处理错误；
- 异常被吞掉，统一返回成功；
- 前后端字段名称、类型或编码不一致；
- 并发、事务、缓存和重试处理错误；
- 修复一个问题时引入回归问题。

### 运行和环境阶段

- 配置、依赖、脚本或数据库版本不一致；
- 网络、硬件、磁盘、内存或第三方服务故障；
- 浏览器、操作系统、设备或屏幕尺寸兼容问题；
- 生产数据规模、权限和流量与测试环境差异明显。

## 3-1.6 课堂案例：QQ、电话和业务用例

### QQ 账号验证

假设规则为“账号必须是 6～10 位自然数”，可以设计：

- 合法代表值：`123456`、`1234567890`；
- 长度不足：`12345`、空值；
- 长度超限：`12345678901`；
- 非数字：`abcdef`、`12a456`；
- 格式风险：负数、小数、前后空格、全角数字；
- 业务风险：已存在账号、被冻结账号、未注册账号。

如果输入 `1234` 后程序显示“合法”，这是一个功能错误；如果程序报错但没有任何提示，也可能同时存在易用性问题。

### 城市电话验证

电话由区号、前缀、后缀等字段组成时，需要分别检查：

- 区号是否为空、长度是否合法、是否允许前导 0；
- 前缀是否必须为 1 开头或不能为 0 开头；
- 后缀长度和数字规则；
- 各字段之间的组合关系；
- 输入非数字、空格、特殊符号、超长值后的行为。

不能只验证三个字段各自合法，还要验证“组合后是否符合完整电话号码规则”。

### 文件输出业务

课件和 Excel 中有“第一列非 A 或 B、第二列非数字”的案例。测试时既要记录输入和实际输出，也要把需求要求的每个输出分别写清楚。例如：

- 输入：第一列 `C`，第二列 `a`；
- 需求预期：第一列不成立输出 `L`，第二列不成立输出 `M`，最终应同时输出 `M、L`；
- 实际结果：只输出 `L`；
- 结论：第二个条件的错误提示或结果被遗漏，属于功能错误。

# 3-2 缺陷介绍

## 3-2.1 缺陷报告的核心内容

一个缺陷报告至少要回答六个问题：

| 要回答的问题 | 对应字段 | 写作要点 |
| --- | --- | --- |
| 发生了什么问题 | 缺陷标题 | 一句话概括对象、条件和错误现象 |
| 在什么条件下发生 | 前置条件 | 写清环境、账号、状态、数据和权限 |
| 如何复现 | 复现步骤 | 按实际操作顺序编号，步骤可执行 |
| 应该是什么 | 预期结果 | 引用需求规则，写可验证的结果 |
| 实际是什么 | 实际结果 | 只写实际观察到的现象，不推测根因 |
| 如何证明 | 附件和备注 | 截图、录屏、日志、请求响应、SQL 结果等 |

## 3-2.2 缺陷提交要素

课程重点介绍了以下要素，企业工具的字段名称可能略有差异：

1. **缺陷编号**：系统自动生成的唯一标识，便于沟通和追踪。
2. **缺陷标题**：描述核心问题，避免只写“有 Bug”“功能不对”。
3. **项目/模块**：说明缺陷属于哪个产品、版本和功能模块。
4. **严重程度 Severity**：说明问题对系统或业务的影响。
5. **优先级 Priority**：说明应该多快修复。
6. **缺陷类型**：代码错误、设计缺陷、兼容性问题、性能问题、数据问题、安全问题等。
7. **前置条件**：复现问题前必须满足的条件。
8. **复现步骤**：让其他人按步骤得到同样问题。
9. **测试数据**：账号、密码、输入值、文件、接口参数等。
10. **预期结果**：符合需求的正确行为。
11. **实际结果**：当前版本真实行为。
12. **发现版本、环境**：版本号、构建号、浏览器、系统、设备、接口环境。
13. **附件**：截图、视频、日志、抓包、数据库结果。
14. **处理人和抄送人**：明确责任人和需要知会的角色。
15. **状态、解决方案和验证结果**：记录缺陷后续流转。

## 3-2.3 严重程度和优先级

### 严重程度 Severity

课程使用 S1～S4 的表达，可以按项目规则映射为 Blocker、Critical、Major、Minor 等名称：

| 级别 | 含义 | 典型例子 |
| --- | --- | --- |
| S1 严重 | 主流程阻断、数据丢失、系统崩溃、重大安全或资金风险 | 无法登录、支付重复扣款、核心数据被覆盖 |
| S2 一般 | 次要功能不可用或主功能部分异常，但有替代路径 | 搜索筛选条件失效、部分用户无法上传头像 |
| S3 微小 | UI、文案、易用性、轻微兼容性问题 | 按钮错位、提示词错误、颜色不符合规范 |
| S4 建议 | 优化建议或体验改进，不影响当前功能完成 | 增加快捷入口、优化提示语、增加排序方式 |

严重程度描述“影响有多大”，不描述“什么时候修”。

### 优先级 Priority

课程使用 P0～P2：

| 级别 | 处理建议 | 典型情形 |
| --- | --- | --- |
| P0 | 立即处理，通常要求当天或 24 小时内响应 | 线上阻断、核心数据错误、重大安全风险 |
| P1 | 当前版本发布前必须修复 | 核心功能明显异常、重要客户路径不可用 |
| P2 | 可排入下一个版本或迭代处理 | 低频问题、轻微 UI 问题、体验改进 |

严重程度和优先级不一定相同：

- 一个 S1 问题通常是 P0 或 P1；
- 一个 S3 文案问题可能因活动上线而被提升为 P1；
- 一个 S2 低频后台问题可能暂定 P2；
- 优先级由业务价值、发布计划、影响用户数、风险和修复成本共同决定。

## 3-2.4 缺陷状态与生命周期

常见状态包括：

```text
New / 新建
  ↓ 测试负责人或开发确认
Open / 已确认
  ↓ 开发修复
Fixed / 已修复
  ↓ 测试重测
Verified / 已验证
  ↓ 关闭
Closed / 已关闭
```

实际项目还需要处理分支：

- **Rejected / 拒绝**：不是缺陷、需求如此、环境问题或重复缺陷；必须写明理由。
- **Duplicate / 重复**：关联已有缺陷，不删除证据。
- **Postponed / 延期**：确认是问题，但本版本不修；应记录版本和风险。
- **Cannot Reproduce / 无法复现**：信息不足或环境差异，不能直接等同于“无问题”。
- **Reopened / 重新打开**：重测失败、修复不完整或回归再次失败。

### 重测和回归的区别

- **重测**：验证开发针对该缺陷做的修复是否有效。
- **回归**：确认修改没有影响相关模块、上下游流程或其他功能。

只做重测不做回归，容易出现“当前问题修好了，但登录、支付、权限等关联功能坏了”的情况。

## 3-2.5 缺陷类型建议

除了课程中的代码错误、兼容性、设计、性能问题，工作中还可使用：

- 功能缺陷；
- UI/交互缺陷；
- 数据缺陷；
- 接口协议缺陷；
- 权限与安全缺陷；
- 配置和部署缺陷；
- 文档和提示语缺陷；
- 兼容性缺陷；
- 性能、稳定性和可靠性缺陷。

分类的目的是统计和改进，不要为了“选一个看起来专业的类型”而猜测根因。

# 3-3 缺陷编写

## 3-3.1 标准缺陷报告模板

```text
缺陷标题：
项目/模块：
关联需求/用例：
发现版本：
测试环境：
严重程度：
优先级：
缺陷类型：
前置条件：
复现步骤：
1.
2.
3.

测试数据：
预期结果：
实际结果：
复现概率：必现 / 偶现（约 X/X 次）
附件：截图、录屏、日志、请求响应、数据库结果
备注：影响范围、临时规避方案、关联缺陷
```

如果项目工具已有字段，不要把所有内容堆进备注；应优先填入结构化字段，方便筛选、统计和报表。

## 3-3.2 缺陷标题写作

好的标题可以让开发在列表页快速理解问题。推荐结构：

```text
[模块/页面] + [触发条件或关键数据] + [实际异常]
```

示例：

- 差：登录有 Bug。
- 好：登录页输入错误密码后，未提示错误信息仍跳转到首页。
- 差：QQ 不合法。
- 好：QQ 验证输入 4 位自然数 `1234` 时，页面错误提示“合法”。
- 差：注册失败。
- 好：注册页输入已注册手机号提交后，未提示账号已存在，接口返回 500。

标题要求：

1. 对象明确：哪个页面、接口、字段或业务模块；
2. 条件明确：什么输入、什么角色、什么状态；
3. 现象明确：错误提示、状态、数据或跳转结果；
4. 避免猜根因：不要在未确认时写“数据库连接错误”；
5. 一个标题描述一个问题，不要把多个问题串在一起。

### 课程中的三种标题组织方式

课程使用“文件两列输入后输出不完整”的案例，给出了三种可以快速说明差异的写法：

1. **测试数据 + 实际结果（预期结果）**：第一列输入非 A/B、第二列输入非数字，实际只输出 L（预期输出 M、L）。
2. **测试数据 + 实际结果（需求规则）**：第一列输入非 A/B、第二列输入非数字，实际只输出 L（需求：两个条件不成立时分别输出 L、M）。
3. **测试数据 + 预期结果（实际结果）**：第一列输入非 A/B、第二列输入非数字，预期输出 M、L（实际只输出 L）。

这三种方式的本质都是让读者快速看到“输入条件、实际现象和正确规则”的差异。企业中仍应优先遵循项目标题规范，并避免标题过长；复杂条件可以放到正文。

## 3-3.3 复现步骤写作

### 步骤的基本要求

- 从可复现的前置状态开始；
- 每一步只描述一个动作或一个紧密相关的动作；
- 写明操作对象和输入数据；
- 不能使用“正常操作”“随便输入”“点击相关按钮”等模糊表达；
- 需要说明账号角色、浏览器、设备、订单状态等上下文；
- 如果问题是偶现，应记录复现次数和概率。

### 示例：QQ 验证缺陷

```text
前置条件：打开 QQ 账号验证程序。
复现步骤：
1. 在 QQ 账号输入框输入 1234。
2. 点击“验证”按钮。
预期结果：提示“账号长度必须为 6～10 位自然数”，不允许通过。
实际结果：页面提示“合法”，验证通过。
```

## 3-3.4 预期结果和实际结果

预期结果要能与需求逐条对应，避免写成“应该正确”“符合要求”。

| 不推荐 | 推荐 |
| --- | --- |
| 页面正常 | 页面显示“手机号格式错误”，光标停留在手机号输入框，表单不提交 |
| 登录成功 | 返回首页，显示当前用户名，服务端返回 200，Token 写入安全存储 |
| 不能输入 | 输入非法字符后不被接受，并显示格式提示 |
| 数据正确 | 订单金额等于商品金额减优惠金额加运费，精确到 2 位小数 |

实际结果只写观察到的事实：

- “点击提交后页面无响应，网络请求持续 30 秒后超时”；
- “接口返回 HTTP 500，响应体为 `NullPointerException`”；
- “页面显示成功，但刷新后订单仍为待支付”；
- “只显示 `L`，没有显示需求要求的 `M`”。

## 3-3.5 附件、日志和隐私

附件要能帮助定位问题，文件名应包含模块、时间、版本和缺陷编号，例如：

```text
BUG-1023_register_500_20260919_1430.png
BUG-1023_register_response.json
BUG-1023_console.log
```

注意：

- 脱敏手机号、身份证号、银行卡号和真实姓名；
- 不把生产密码、Token、Cookie 或密钥直接上传到缺陷系统；
- 日志中只保留定位所需部分；
- 录屏从复现前开始，避免缺少关键前置操作；
- 接口缺陷同时保留请求方法、URL、关键请求头、请求体和响应码。

## 3-3.6 缺陷评审

缺陷评审是为了确认缺陷的有效性、影响和处理方式，不是为了否定测试人员。

建议评审以下内容：

1. 是否违反需求、设计或已确认规则？
2. 是否可复现？复现步骤是否足够？
3. 是否与已有缺陷重复？
4. 严重程度和优先级是否合理？
5. 是否影响其他模块或已有数据？
6. 是否需要立即停止测试或阻断发布？
7. 是否需要产品、研发、运维或安全人员共同确认？
8. 是否需要补充自动化回归用例？

遇到“按需求就是这样”的反馈时，应回到需求、原型、接口文档、产品确认记录或历史版本证据，不要用个人偏好争论。

## 3-3.7 提交前自检清单

- [ ] 标题能独立说明问题；
- [ ] 一个缺陷只描述一个独立问题；
- [ ] 前置条件完整；
- [ ] 步骤按顺序可执行；
- [ ] 测试数据真实且已脱敏；
- [ ] 预期结果有依据；
- [ ] 实际结果是事实而非猜测；
- [ ] 已标明版本、环境和复现概率；
- [ ] 已附上必要证据；
- [ ] 已检查是否重复提交；
- [ ] 严重程度和优先级有理由；
- [ ] 不包含密码、Token、密钥等敏感信息。

## 3-3.8 测试、开发和产品的职责边界

缺陷流转中常见的职责分工是：

- **测试人员**：确认问题、提交缺陷、补充证据、验证修复、执行回归、关闭或重新打开缺陷；
- **开发人员**：复现和定位问题、评估修复方案、修改代码、完成自测并提供修复版本；
- **产品或业务人员**：确认需求规则、业务价值、验收口径和需求变更；
- **项目负责人**：协调优先级、资源、修复时间和发布风险。

即使测试人员具备开发能力，也不应在未经项目授权和代码评审的情况下直接修改开发负责的代码。否则会破坏责任边界、版本管理和变更审计。

### 开发不认可缺陷时如何处理

1. 先确认环境、数据和步骤，确保问题可复现。
2. 提供需求、原型、接口文档、验收标准或历史版本作为依据。
3. 说明用户影响和业务风险，不把讨论变成个人观点之争。
4. 如果需求没有明确标准，邀请产品、业务和开发共同评审并形成书面结论。
5. 若确认不是缺陷，以 Rejected、By Design 或需求变更等方式处理并记录理由。
6. 若确认是缺陷但当前版本不修，记录延期版本、风险、临时规避方案和决策人。
7. 不因“实现困难”直接放弃问题；实现成本由团队评估，测试仍需如实说明质量风险。

# 3-4 缺陷管理工具

## 3-4.1 Excel 管理缺陷

课程案例使用 Excel 记录缺陷，常见列包括：

| 字段 | 作用 |
| --- | --- |
| 缺陷编号 | 唯一标识问题 |
| 缺陷标题 | 快速识别问题 |
| 项目/模块 | 统计模块质量 |
| 优先级 | 安排修复顺序 |
| 前置条件 | 说明复现环境 |
| 测试步骤 | 记录操作路径 |
| 测试数据 | 记录输入值 |
| 预期结果 | 需求要求的行为 |
| 实际结果 | 当前版本实际表现 |
| 严重程度 | 衡量影响大小 |
| 缺陷状态 | 跟踪生命周期 |
| 指派给 | 明确责任人 |
| 发现版本/修复版本 | 做版本追踪 |
| 提交人/提交时间 | 保留审计信息 |

Excel 适合学习、临时记录和小团队，但要注意：

- 使用下拉选项统一状态、优先级和模块名称；
- 使用唯一编号，不能多人随意手写同号；
- 用筛选查看“未关闭缺陷”“P0/P1”“某版本”等集合；
- 重要修改保留版本记录；
- 不要把多个问题写在同一个单元格里；
- 逐步迁移到禅道、Jira、Azure DevOps 等协作工具。

## 3-4.2 禅道的定位和特点

课程介绍的禅道是国产、免费、开源、简单、轻量级的项目管理工具，支持产品管理、项目管理和质量管理的融合。

典型协作角色：

- 产品部门：提出目标、需求和验收规则；
- 项目经理：协调资源、计划和交付；
- 研发团队：设计、开发和修复；
- 测试团队：设计用例、执行测试、发现和验证缺陷。

工具的价值不只是“把 Excel 换成网页”，还包括：

- 需求、任务、用例、缺陷之间可以关联；
- 可以按产品、项目、版本、模块和人员筛选；
- 能查看缺陷趋势、关闭率、遗留问题和版本风险；
- 通过状态流转减少口头遗漏；
- 形成可追踪的质量证据。

## 3-4.3 使用禅道提交缺陷的通用流程

不同版本界面可能不同，但通用步骤如下：

1. 登录系统，进入产品、项目和当前迭代。
2. 确认当前版本、模块和需求关联关系。
3. 进入“测试/缺陷”模块，点击新建缺陷。
4. 填写标题、严重程度、优先级、类型、环境和版本。
5. 填写前置条件、步骤、预期、实际和测试数据。
6. 上传截图、录屏、日志或接口证据。
7. 指派给开发人员，必要时抄送产品或项目负责人。
8. 保存后检查缺陷详情，确认字段没有错位或遗漏。
9. 开发处理后，测试根据修复版本执行重测和回归。
10. 在缺陷中补充验证结果，关闭或重新打开。

## 3-4.4 禅道管理测试用例

缺陷和用例应互相链接：

- 用例说明“验证什么”；
- 缺陷说明“哪里不符合预期”；
- 执行结果说明“这次版本是否通过”；
- 修复版本说明“哪个构建已修复”。

一条用例失败时，不一定只提交一条缺陷：如果同一用例暴露了两个相互独立的问题，应拆成两个缺陷；如果多个步骤都是同一根因导致的同一问题，可以合并并完整描述影响范围。

## 3-4.5 缺陷统计和质量分析

就业时不仅要会“提 Bug”，还要能从数据中给出判断：

- 新增缺陷数、关闭缺陷数和遗留缺陷数；
- 按严重程度和优先级分布；
- 按模块、版本、开发人员分布；
- 缺陷平均修复时长；
- 缺陷重开率和无效缺陷率；
- 测试执行通过率和缺陷发现率；
- 缺陷在需求、设计、开发还是测试阶段被发现；
- 版本发布前是否仍存在 P0/P1 或未评审问题。

这些数据不能简单用来评价个人，要结合需求复杂度、版本规模和测试投入分析。

# 3-5 注册功能案例：从测试点到缺陷

## 3-5.1 注册需求假设

以下案例综合课程视频、注册 XMind 和就业中的常见规则：

1. 手机号为 11 位数字，且不能是已注册手机号。
2. 密码由字母和数字组成，长度 6～16 位。
3. 图片验证码和短信验证码必须正确且在有效期内。
4. 验证码错误或为空时不能提交注册。
5. 用户必须同意协议后才能提交。
6. 注册成功后提示成功并跳转到登录页或首页，行为应与需求一致。
7. 注册页面需要兼容项目支持的浏览器和移动端尺寸。

## 3-5.2 注册测试点

### 手机号

- 合法：11 位、未注册、正常号段；
- 长度边界：10 位、11 位、12 位；
- 空值、全空格、前后空格；
- 字母、汉字、特殊字符、带短横线；
- 已注册手机号；
- 发送验证码频率、倒计时和重复点击；
- 弱网、短信服务失败、验证码过期。

### 密码

- 6 位、16 位合法边界；
- 5 位、17 位非法边界；
- 纯数字、纯字母、字母数字组合；
- 空值、空格、前后空格；
- 特殊字符、中文、全角字符；
- 显示/隐藏密码按钮；
- 两次密码不一致；
- 粘贴、复制、浏览器自动填充和密码强度提示。

### 图片验证码和短信验证码

- 正确、错误、为空、过期、重复使用；
- 验证码刷新后旧码是否失效；
- 大小写规则；
- 连续输错后的限制；
- 错误提示是否准确且不泄露敏感信息。

### 协议和提交

- 未勾选协议不能提交；
- 勾选后可以提交；
- 取消勾选后按钮状态是否恢复；
- 连续点击是否产生重复请求；
- 注册成功后的跳转、提示和账号状态；
- 注册失败后输入内容是否保留，是否允许重试。

### 兼容性和 UI

- Edge、Chrome、Firefox、Safari 等项目支持浏览器；
- Windows、Android、iOS 及不同屏幕尺寸；
- 键盘 Tab 顺序、回车提交、焦点位置；
- 错误提示不遮挡输入框；
- 按钮、验证码图片和协议链接可点击；
- 文字、颜色和对比度满足可读性要求。

# 三、章节综合复习

## 3.1 高频易错点

1. **严重程度不等于优先级**：影响大不代表一定最先修，还要考虑业务和版本。
2. **实际结果不能写猜测根因**：测试人员发现的是现象，根因需要定位验证。
3. **一个缺陷一个问题**：同一页面有“文案错误”和“接口 500”，应分别提交。
4. **无法复现不等于无缺陷**：先补充环境、日志、数据和复现概率。
5. **开发说不是 Bug 也要看依据**：回到需求、原型、验收标准和产品确认。
6. **修复后要重测和回归**：不能只确认当前页面不再报错。
7. **附件不能泄露敏感数据**：日志、截图和抓包都需要脱敏。
8. **测试工具不是目的**：禅道记录的是可追踪事实，不是把字段填满。
9. **注册测试不能只测一次成功**：输入校验、重复注册、验证码、协议、并发和兼容性同样重要。
10. **关闭缺陷要有证据**：记录验证版本、环境、结果和关联回归用例。

## 3.2 习题测试与答案

### 习题 1：判断是否为缺陷

某需求明确规定“密码长度必须为 6～16 位”。输入 5 位密码后，前端没有提示，接口返回 200 并创建成功。是否为缺陷？

**答案**：是。它违反了明确需求，属于功能和安全相关缺陷。若前端和后端均未校验，可以在一个缺陷中描述完整影响，也可以按团队规则拆分为前端校验缺失和服务端校验缺失两个缺陷。

### 习题 2：严重程度和优先级

管理后台一个不常用页面的按钮文案错了，但当天要进行客户演示。严重程度和优先级如何判断？

**答案**：严重程度可定为 S3；由于客户演示临近，优先级可以提升为 P1。严重程度看影响性质，优先级看业务时间和处理紧急性。

### 习题 3：标题改写

把“注册有问题”改成合格的缺陷标题。

**答案**：例如“注册页输入已注册手机号并提交后返回 HTTP 500，未提示账号已存在”。标题同时包含模块、触发条件和实际异常。

### 习题 4：实际结果改写

“数据库连接池配置错误导致接口超时”是否适合作为实际结果？

**答案**：不适合作为未经验证的实际结果。应写成“点击查询后 30 秒无响应，接口返回 504；服务端日志显示请求超时”。数据库连接池是否为根因，应由后续定位确认。

### 习题 5：状态流转

开发将缺陷改为“已修复”，测试重测仍能复现，应该如何处理？

**答案**：将缺陷重新打开，补充重测版本、环境、步骤和证据；如果发现是另一个独立问题，再新建缺陷并互相关联。

### 习题 6：是否重复提交

两个页面都因为同一个接口字段为空而显示错误。应该提交一条还是两条？

**答案**：先判断是否同一根因和同一修复点。如果同一接口问题可同时解释两个页面，通常提交一条主缺陷，写清两个页面的影响并关联用例；如果修复点不同或责任模块不同，则拆分提交。

### 习题 7：Excel 字段

缺陷表中为什么不能只保留“标题、截图、状态”三列？

**答案**：缺少前置条件、步骤、测试数据、预期和实际结果，其他人无法稳定复现，也无法判断问题是否真正修复；缺少版本和优先级也无法进行发布风险管理。

### 习题 8：注册功能

注册按钮连续点击 5 次产生 5 条账号记录，属于什么问题？

**答案**：属于重复提交/幂等性缺陷，可能同时造成数据重复和业务风险。应检查前端按钮防重复、服务端幂等键、数据库唯一约束和失败重试策略。

### 习题 9：无效缺陷处理

开发反馈“需求就是这样”，测试人员应该直接关闭缺陷吗？

**答案**：不应直接关闭。应要求提供需求、原型或产品确认依据；若确认不是缺陷，将状态改为拒绝并记录理由；若需求本身不清晰，应由产品确认后决定关闭、转需求变更或继续修复。

### 习题 10：缺陷关闭

关闭缺陷前至少要记录哪些内容？

**答案**：验证版本/构建号、测试环境、重测步骤、实际验证结果、关联回归用例、是否仍有影响，以及关闭人和时间。

## 4.4 参考答案：3 条缺陷报告

### BUG-REG-001：密码长度 5 位仍可注册

```text
严重程度：S2
优先级：P1
类型：功能/安全
状态：New
前置条件：准备未注册手机号，验证码服务正常。
步骤：
1. 打开注册页。
2. 输入未注册手机号 13800138000。
3. 输入密码 a1234。
4. 输入正确验证码，勾选协议并提交。
预期：提示密码必须为 6～16 位，注册请求不应成功。
实际：注册成功，账号使用 5 位密码创建。
证据：页面录屏、注册接口请求响应、构建号。
```

### BUG-REG-002：已注册手机号返回 HTTP 500

```text
严重程度：S2
优先级：P1
类型：接口/错误处理
状态：New
前置条件：手机号 13800138001 已存在。
步骤：
1. 打开注册页。
2. 输入已注册手机号。
3. 输入合法密码、正确验证码并勾选协议。
4. 点击注册。
预期：提示手机号已注册并引导登录。
实际：页面提示系统异常，接口返回 HTTP 500。
证据：响应体、服务端日志时间点、截图。
```

### BUG-REG-003：重复点击注册产生多条请求

```text
严重程度：S1
优先级：P0
类型：数据/幂等性
状态：New
前置条件：合法注册数据，网络延迟约 2 秒。
步骤：
1. 填写合法手机号、密码和验证码。
2. 在响应返回前连续点击注册按钮 5 次。
3. 查询账号或注册请求日志。
预期：只接受一次注册请求，最多创建一条账号记录。
实际：产生 5 次请求并创建重复记录。
```

## 4.6 参考答案：回归范围

- 密码校验修改：注册、登录、修改密码、找回密码、密码强度提示；
- 已注册手机号错误处理：注册接口、登录引导、短信发送限制、前端错误提示；
- 防重复提交：注册、发送验证码、登录、支付等复用同一提交组件的功能；
- 数据库唯一约束修改：注册、账号查询、后台用户管理和数据迁移脚本。

## 4.7 面试表达示例

> 我在注册模块中先根据需求提取手机号、密码、验证码、协议、提交和兼容性测试点，再用等价类和边界值覆盖 10/11/12 位手机号以及 5/6/16/17 位密码。执行时发现密码长度校验缺失、已注册手机号返回 500、注册按钮重复点击产生多条请求。我分别记录了前置条件、复现步骤、预期和实际结果，并附上截图、网络请求和日志。评审时根据影响将重复注册定为高严重度和高优先级，其他问题定为一般严重度、发布前修复。开发提交新版本后，我先重测原缺陷，再回归登录、验证码、找回密码和账号唯一性，最后在禅道中补充验证版本和结果并关闭。
