# 阶段一：测试基础

## 第一章：测试基础

本章目标是建立一套可以直接用于项目的测试基础：知道测试在验证什么，能够从需求中找出风险，能写出别人可以执行的测试用例，并能用测试结论支持发布决策。学习时请把“记住定义”和“能在案例中做出来”作为两个不同的验收层次。

---

# 1-1 阶段目标及路线

## 1-1.1 视频原讲提炼

这一节的核心不是立即学习某个工具，而是建立“软件测试从基础到就业”的全局路线。课程路线可以归纳为三条主线：

1. **基础篇**：软件测试概念与分类、测试流程、需求分析、测试用例设计、测试计划、测试报告和缺陷管理。
2. **进阶篇**：接口测试、JMeter、Postman、Pytest、Requests、Web 自动化、Selenium 和性能测试。
3. **项目实战篇**：在金融、银行、电商等项目中，把需求、环境、用例、缺陷、接口、数据库、Linux 和报告串起来。

课程强调的就业能力不只是“会点击页面”或“会使用一个工具”，还包括：

- 能看懂需求并发现歧义；
- 能从业务流程中提取测试点；
- 能编写别人可以执行的测试用例；
- 能执行用例、记录实际结果、提交和跟踪缺陷；
- 能使用数据库、接口和 Linux 进行定位；
- 能清楚解释测试结论、风险和上线建议。

## 1-1.2 学习顺序与能力地图

推荐按照下面的顺序学习：

```text
测试思维
  -> 软件测试概念与分类
  -> 测试流程与需求分析
  -> 测试点和测试用例设计
  -> 缺陷管理、测试计划、测试报告
  -> HTTP、接口、SQL、Linux
  -> JMeter/Requests/Pytest/Selenium
  -> 性能测试、持续集成和项目表达
```

### 初级功能测试能力

至少要能完成：

1. 阅读登录、注册、搜索、下单等功能需求；
2. 区分正常流程、异常流程、边界条件、权限和兼容性风险；
3. 编写包含前置条件、步骤、数据和预期结果的用例；
4. 执行用例并保存截图、请求、日志等证据；
5. 提交规范缺陷，验证修复后进行回归；
6. 输出简短的测试结论。

### 中级测试能力

课程后续涉及的接口、数据库和 Linux，目的不是增加工具名，而是让测试人员能够穿透页面定位问题：

- 用 SQL 准备测试数据并校验数据是否正确落库；
- 用接口工具验证状态码、业务码、鉴权、参数和异常响应；
- 用 Linux 查看服务、进程、端口和日志；
- 用请求 ID、用户 ID 或订单号关联页面、接口、日志和数据库结果。

### 自动化和性能能力

自动化应建立在手工测试思维之上。正确顺序是：

1. 先能够判断业务是否正确；
2. 识别稳定、重复、高频的检查项；
3. 编写明确的断言、数据准备和清理逻辑；
4. 处理失败重试、日志、报告和环境差异；
5. 最后再接入 Jenkins 等持续集成工具。

## 1-1.2.1 为什么基础阶段决定就业上限

初级岗位招聘时经常写“熟悉功能测试、测试用例、缺陷管理、接口和数据库”。这些词看起来很多，实际都围绕同一个能力：**把需求转化成可验证的质量证据**。

例如产品提出“用户可以下单”，测试人员至少要继续追问：

- 什么用户可以下单？游客、普通用户还是会员？
- 商品库存为 0 时是否允许提交？
- 优惠券、积分和运费如何计算？
- 支付成功但回调超时，订单状态是什么？
- 用户重复点击提交按钮会不会生成两笔订单？
- 下单后页面、接口、订单表和库存表分别应该是什么状态？

不会追问这些问题的人，即使熟悉自动化工具，也很容易遗漏真实业务缺陷。基础知识的价值就在于帮助你发现“需求没有说清楚的地方”和“用户真正会遇到的风险”。

## 1-1.2.2 从学习知识到工作产出的转换

| 学习中的说法 | 工作中的产出 |
|---|---|
| 学习测试分类 | 在测试计划中选择本次版本需要的测试类型 |
| 学习测试流程 | 能说明当前版本处于哪个阶段、下一步谁负责什么 |
| 学习等价类 | 用较少数据覆盖大量同类输入 |
| 学习边界值 | 优先检查最容易出错的临界位置 |
| 学习场景法 | 覆盖从开始到结束的真实业务链路 |
| 学习测试用例 | 形成可执行、可回归、可追踪的测试资产 |
| 学习质量模型 | 不只看功能，还能发现安全、兼容、可靠性问题 |

学习每一个术语时，都应问自己三个问题：**它解决什么问题？什么时候使用？产出什么结果？**

## 1-1.2.3 初级测试人员的一天

一个典型工作日可能包含以下活动：

1. 参加站会，确认版本、阻塞事项和当天目标；
2. 阅读需求和原型，提出规则、权限、异常和验收标准问题；
3. 根据需求拆分测试点，编写或补充测试用例；
4. 确认测试环境、构建版本、账号和数据；
5. 先执行冒烟，再执行核心流程和异常流程；
6. 对失败结果进行初步定位，提交缺陷并附证据；
7. 跟踪开发修复，执行回归并更新缺陷状态；
8. 在迭代结束时整理测试结果、未解决风险和发布建议。

这说明测试岗位既需要技术操作，也需要沟通、记录、判断和风险意识。

## 1-1.3 就业补充：如何证明自己“会测试”

面试中“我看过视频”“我会 JMeter”说服力有限。更好的证明方式是准备可展示的成果：

| 能力 | 可展示成果 |
|---|---|
| 测试基础 | 一张测试生命周期图和分类矩阵 |
| 用例设计 | 登录、注册或下单模块 20 条以上用例 |
| 缺陷管理 | 3 条包含环境、步骤、实际/预期结果和证据的 Bug |
| 接口测试 | 一个带参数化、关联和断言的接口集合 |
| 数据库 | 测试数据准备 SQL 和结果校验 SQL |
| Linux | 一份从日志中定位错误的排查记录 |
| 项目表达 | 一页测试总结，说明范围、通过情况、遗留风险和建议 |

**重要判断标准**：学习进度不应只按“看完多少视频”计算，而应按“能否独立产出、执行、解释和复盘”计算。

## 1-1.4 本节练习与答案

### 练习 1：为什么不建议刚学测试就直接学习 Selenium？

**答案**：Selenium 主要解决浏览器操作，不负责判断业务是否正确。如果没有需求分析、测试设计和断言基础，容易只会点击页面，无法覆盖异常流程、权限、数据一致性和回归风险。

### 练习 2：面试官问“你会 JMeter 吗”，如何回答更有说服力？

**答案**：不要只回答“会”。应说明使用场景和产出，例如：“我用 JMeter 调试登录和订单接口，使用 CSV 参数化、JSON 提取器做接口关联，用断言校验状态码和业务字段，并生成报告或接入 Jenkins。”如果没有真实项目，应明确说是练习项目，不要虚构工作经历。

### 练习 3：为本节建立一个验收标准。

**答案**：能够画出自己的学习路线，解释每个阶段解决的问题，并提交一个登录模块测试资产包，至少包括测试点、10 条用例、1 条规范 Bug 和一页测试结论。

# 1-2 测试相关概念

## 1-2.1 什么是软件

软件不仅是安装包或页面，还包括：

- 程序代码；
- 配置文件和环境变量；
- 数据库和缓存中的数据；
- 接口、消息和第三方服务；
- 帮助文档、接口文档、需求文档和部署脚本；
- 用户、权限和业务流程。

因此测试一个系统时，不能只点击前端页面。页面看起来正确，并不代表接口、数据库、权限、日志和异常恢复都正确。

## 1-2.2 软件测试定义与目的

### 课程定义

软件测试是**使用技术手段验证软件是否满足使用需求**的活动。

### 测试目的

1. 发现缺陷，降低软件上线后的风险；
2. 验证功能和非功能需求是否得到满足；
3. 为发布或上线提供质量信息；
4. 通过测试证据帮助团队进行风险决策。

测试不是证明软件“绝对没有 Bug”。测试只能在规定范围、环境、数据和时间内提供证据，说明已发现的问题、未覆盖的风险和当前质量状态。

### 测试、验证与确认

- **验证（Verification）**：检查产品是否按照要求被正确构建，例如需求、设计、代码和用例评审；常见于静态测试。
- **确认/确认有效性（Validation）**：检查构建出来的产品是否真正满足用户需要，例如在真实业务流程中执行系统测试和验收测试。

在工作中可以简单理解为：验证偏向“有没有按规格做”，确认偏向“做出来的东西对用户有没有用”。二者都需要测试人员参与。

### 测试人员不应作出的绝对承诺

以下说法不严谨：

- “我测试过了，所以肯定没有 Bug”；
- “所有用例通过，所以一定可以上线”；
- “代码覆盖率 100%，所以质量没有问题”。

更专业的表达是：

> 在版本、环境和测试范围明确的前提下，核心功能和指定风险已完成验证；当前未发现阻塞性问题，但仍存在已知遗留风险或未覆盖范围，建议由项目负责人结合风险决定是否发布。

### 测试的基本原则

1. **测试能够发现缺陷，但不能证明没有缺陷**；
2. **穷尽测试通常不可行**，需要使用风险分析和测试设计方法挑选高价值数据；
3. **缺陷具有集群性**，问题往往集中在复杂、频繁变更或历史上出过问题的模块；
4. **杀虫剂悖论**：长期只执行同一批用例，会逐渐发现不了新的问题，需要定期补充探索性、边界和异常测试；
5. **测试活动应尽早开始**，需求阶段发现歧义比上线后修复缺陷成本低；
6. **不同场景需要不同方法**，功能、性能、安全和易用性不能只用一种测试方式代替。

## 1-2.3 测试主流技能

### 功能测试

验证系统“能不能完成需求规定的事情”，例如注册、登录、搜索、下单、退款、权限控制和错误提示。

### 自动化测试

把稳定、重复和高频的检查转化为脚本或自动化流程。自动化是执行手段，不等于测试思维；自动化脚本仍然需要可靠的测试数据和明确断言。

### 接口测试

绕过页面直接验证 HTTP/RPC 等接口的参数、状态码、业务码、鉴权、数据结构、幂等性和异常处理。接口测试通常反馈更快，也更容易定位服务问题。

### 性能测试

验证响应时间、吞吐量、并发、稳定性、资源消耗和容量。性能测试必须建立在业务正确和场景明确的基础上，不能只盯着一个平均响应时间。

## 1-2.4 测试分类

分类是不同观察角度，不是互相排斥的标签。同一个“普通用户在 Chrome 中提交订单”的测试，可能同时属于系统测试、黑盒测试、功能测试、兼容性测试和安全权限测试。

### 按测试阶段分类

| 类型 | 测试对象 | 典型特点 |
|---|---|---|
| 单元测试 | 函数、类、最小代码模块 | 粒度小、速度快，通常由开发完成 |
| 集成测试 | 多个模块、服务或接口之间的协作 | 关注字段传递、接口契约、事务和异常传播 |
| 系统测试 | 完整系统 | 在接近真实的环境中验证功能和非功能需求 |
| 验收测试 | 面向客户、业务或最终用户的交付结果 | 判断是否满足合同、业务目标和上线标准 |

验收测试还可以按环境或用户范围区分为内部受控的 Alpha 测试和有限外部用户参与的 Beta 测试。

### 测试阶段之间的关系

单元、集成、系统和验收不是“只能选一个”的岗位名称，而是不同粒度的质量检查：

```text
函数/类
  -> 多模块或服务接口
  -> 完整系统和真实业务流程
  -> 客户/业务最终确认
```

越靠前，反馈通常越快、定位成本越低；越靠后，越接近用户真实使用，但环境和协作成本更高。实际项目需要在多个阶段共同建立质量保障，不能把所有问题都推迟到系统测试。

### 常见分类维度对照

| 分类维度 | 回答的问题 | 示例 |
|---|---|---|
| 测试阶段 | 在产品生命周期哪个层次验证 | 单元、集成、系统、验收 |
| 代码可见度 | 测试时了解多少内部实现 | 黑盒、灰盒、白盒 |
| 测试内容 | 具体验证什么质量属性 | 功能、性能、安全、兼容 |
| 执行目的 | 当前测试为哪个决策服务 | 冒烟、回归、探索性 |
| 执行方式 | 由人执行还是工具执行 | 手工、自动化 |

面试回答分类问题时，先说清楚“按哪个维度分类”，再列举类型，避免把不同维度的术语混成一组。

### 按代码可见度分类

| 类型 | 可见信息 | 关注重点 |
|---|---|---|
| 黑盒测试 | 不依赖源代码实现 | 根据输入、输出和需求验证功能与非功能 |
| 灰盒测试 | 掌握部分架构、接口、数据库或设计信息 | 利用部分内部信息设计更有针对性的测试 |
| 白盒测试 | 可以查看源代码、分支和路径 | 关注语句、分支、条件和路径覆盖 |

**注意**：代码覆盖率高，不代表需求覆盖完整，也不代表断言正确，更不代表没有安全、性能和数据一致性问题。

### 按是否运行程序分类

- **静态测试**：不运行被测程序，检查需求、设计、代码、接口文档或测试用例。需求评审、代码走查、文档检查都可以属于静态测试。
- **动态测试**：运行被测程序并观察结果。手工功能测试、自动化测试、接口测试和性能测试都属于动态测试。

### 按测试内容分类

- **功能性**：功能是否正确、流程是否完整、异常是否符合要求；
- **性能**：响应时间、吞吐量、并发、稳定性、资源消耗；
- **兼容性**：操作系统、浏览器、设备、分辨率、网络和版本兼容；
- **易用性**：用户是否容易理解、学习和完成任务；
- **可靠性**：异常恢复、长时间运行、断网重连、数据不丢失；
- **安全性**：认证、授权、越权、会话、输入校验和敏感数据保护；
- **可维护性**：日志、配置、模块化和故障定位是否方便；
- **可移植性**：系统迁移到其他平台、环境或部署方式时是否正常。

### 按执行目的分类

- **冒烟测试**：版本部署后快速验证启动、登录等核心链路；失败时通常暂停后续全面测试；
- **回归测试**：修复或变更后，验证原问题及受影响区域没有引入新问题；
- **探索性测试**：在学习系统的同时设计和执行测试，适用于需求不完整或风险未知的场景；
- **专项测试**：针对安全、性能、兼容性、可靠性等特定质量属性开展的测试。

### 冒烟、回归、重测的区别

- **冒烟测试**：新版本刚部署时，快速判断版本是否具备继续测试的条件；
- **重测（Retest）**：针对某一条已修复缺陷，按原步骤确认问题是否解决；
- **回归测试**：在重测之外，检查修复或改动是否影响周边功能和核心链路。

例如“登录验证码错误”缺陷修复后，先重测错误提示和接口返回；再回归登录成功、注册、找回密码、锁定策略、第三方登录和冒烟流程。

## 1-2.5 质量模型

Day01 资料中的质量模型重点包括功能、性能、兼容、易用和安全；课件进一步列出八项常见质量属性：

1. **功能性**：功能是否完整、正确，是否符合业务规则；
2. **性能**：在规定负载下的响应、吞吐和资源消耗；
3. **兼容性**：不同系统、浏览器、设备、网络和依赖版本下是否正常；
4. **易用性**：用户是否容易理解、学习和完成操作；
5. **可靠性**：在规定条件和时间内稳定工作并能恢复异常；
6. **安全性**：防止未授权访问、数据泄露、篡改和攻击；
7. **可维护性**：分析、修改、测试和定位问题的难易程度；
8. **可移植性**：迁移到其他环境、平台或部署方式的难易程度。

测试人员不需要每次都把八项平均覆盖，而应根据业务风险排序。例如支付系统要重点关注功能、可靠性、安全、性能和数据一致性；内容展示站点可能更关注兼容性、易用性和性能。

### 质量属性举例

以“支付订单”为例：

| 质量属性 | 需要思考的问题 |
|---|---|
| 功能性 | 金额、优惠、支付状态和订单状态是否符合规则？ |
| 性能 | 高峰期提交订单和查询结果是否在可接受时间内返回？ |
| 兼容性 | 不同浏览器、移动设备和网络环境是否都能完成支付？ |
| 易用性 | 用户能否看懂失败原因并顺利重试？ |
| 可靠性 | 支付回调延迟、重复通知或断网后能否恢复？ |
| 安全性 | 是否能越权支付他人订单、篡改金额或重放请求？ |
| 可维护性 | 出错时是否有足够日志和请求 ID 供定位？ |
| 可移植性 | 更换部署区域、数据库或运行环境后是否仍可用？ |

同一业务动作往往同时涉及多个质量属性，这也是为什么测试不能只写“点击支付，显示成功”。

## 1-2.6 测试流程

课件和 XMind 的六步主流程是：

1. **需求评审**：理解测什么，发现歧义、遗漏和不可验证的要求；
2. **测试计划**：明确范围、资源、人员、进度、环境、风险和交付物；
3. **用例设计**：把需求转化为测试点、数据、步骤和预期结果；
4. **用例执行**：准备环境和数据，按用例执行并保存实际结果和证据；
5. **缺陷管理**：提交、分派、修复、验证、关闭或重新打开缺陷；
6. **测试报告**：总结执行情况、缺陷、风险、限制和发布建议。

实际企业流程通常还会显式加入环境准备、版本确认、冒烟测试、回归测试、发布评审和上线后观察。流程名称可能不同，但本质都是把需求、风险、执行证据和发布决策串起来。

### 测试流程中的输入和输出

| 阶段 | 主要输入 | 主要输出 |
|---|---|---|
| 需求评审 | 需求、原型、接口文档、验收标准 | 评审问题、确认结论、测试范围 |
| 测试计划 | 需求范围、版本计划、资源和风险 | 测试计划、排期、人员分工 |
| 用例设计 | 需求条目、业务流程、风险 | 测试点、用例、测试数据 |
| 环境准备 | 构建包、配置、账号、依赖服务 | 可用环境、版本记录、数据方案 |
| 用例执行 | 用例、环境、数据 | 实际结果、执行记录、测试证据 |
| 缺陷管理 | 失败结果和证据 | 缺陷单、修复状态、回归结果 |
| 测试报告 | 执行统计、缺陷和风险 | 测试报告、发布建议、遗留风险 |

这样理解流程后，遇到“现在该做什么”时，可以先判断当前阶段缺什么输入、应该产出什么结果，而不是只背六个名称。

### 测试环境补充

课程转写中提到开发环境、测试环境、预发布环境和生产环境。常见理解如下：

- **开发环境（DEV）**：开发人员编码和自测；
- **测试环境（QA/SIT）**：测试人员进行集成和系统测试；
- **预发布环境（UAT/预发布）**：尽量接近生产，用于验收和上线前验证；
- **生产环境（PROD）**：真实用户和真实业务使用的环境。

测试报告中应写清实际执行环境、版本号、浏览器/设备、接口地址和测试数据来源，否则问题很难复现。

## 1-2.7 就业补充：测试工作中的关键习惯

### 测试左移

不要等开发完成后才开始思考测试。需求评审时就提出边界、异常、权限、数据和验收标准问题，可以更早、更低成本地发现缺陷。

### 风险驱动

当时间不足时，优先覆盖资金、权限、登录、核心链路、数据一致性和高频功能。不能只按页面顺序机械执行。

### 证据留存

失败结果至少应保留截图、请求报文、响应报文、时间、版本、账号、数据 ID、日志或录屏中的必要部分。没有证据的“感觉有问题”很难推动修复。

### 入口和出口标准

- 入口标准：需求已评审、版本可部署、环境可用、账号和数据就绪；
- 出口标准：核心用例通过、阻塞性缺陷关闭、遗留风险得到确认，并形成测试结论。

### 优先级和严重程度要区分

用例优先级表示时间有限时先执行什么；缺陷严重程度表示问题对系统或用户的影响。低频安全漏洞可能执行优先级不高，但缺陷严重程度仍然很高。

## 1-2.8 本节练习与答案

### 练习 1：代码分支覆盖率 100% 能否直接发布？

**答案**：不能。还要确认需求覆盖、业务规则、数据一致性、权限、安全、兼容性、性能、已知缺陷和遗留风险。覆盖率只说明执行过分支，不说明需求正确或断言正确。

### 练习 2：ATM 余额不足时拒绝取款并提示，属于哪些测试分类？

**答案**：至少属于系统测试、黑盒测试、动态测试、功能测试和异常流程测试。如果在不同 ATM 设备、网络或操作系统上验证，还可以增加兼容性测试；如果关注密码、卡锁定或越权，还涉及安全测试。

### 练习 3：需求写“页面加载要快”，测试人员应该怎么办？

**答案**：在需求评审中要求量化标准，例如指定页面、网络条件、数据量、并发量和 P95 响应时间。在标准未确认前记录风险，不应自行假设一个数字作为最终验收标准。

# 1-3 测试用例

## 1-3.1 什么是测试用例

测试用例（Test Case）是为了验证某项需求而编制的一组**测试输入、执行条件、操作步骤和预期结果**。它不是一句“测试登录”，而是一份可以由其他人重复执行和判断结果的文档。

### 测试用例的作用

1. 防止漏测；
2. 统一测试执行标准；
3. 便于团队协作、交接和回归；
4. 支持需求追踪和测试覆盖率统计；
5. 为缺陷复现和测试报告提供证据。

一个合格用例应满足：**可执行、可复现、可判定、可追溯、可维护**。

### 好用例与差用例对比

| 维度 | 差用例 | 好用例 |
|---|---|---|
| 标题 | 测试登录 | 错误密码登录时阻止进入首页并提示密码错误 |
| 前置条件 | 无 | 账号已注册、未锁定，QA 环境服务正常 |
| 步骤 | 输入正确数据并提交 | 写清页面入口、字段、按钮和顺序 |
| 数据 | 正确数据 | 给出具体账号、密码、验证码或边界值 |
| 预期 | 结果正确 | 写明页面、接口、数据库可观察结果 |
| 复现性 | 依赖作者记忆 | 其他测试人员可独立执行 |

写用例时要避免三类问题：

1. **步骤过粗**：把多个动作写成一句，执行者不知道在哪一步失败；
2. **预期模糊**：使用“正常”“正确”“提示友好”等无法判断的词；
3. **数据缺失**：没有账号状态、权限、边界值或依赖数据，导致结果不可复现。

## 1-3.2 八大要素

课件、XMind 和 Excel 模板中的八大要素如下：

| 序号 | 要素 | 编写要求 |
|---:|---|---|
| 1 | 用例编号 | 唯一且稳定，建议使用“项目简称_模块_编号”，如 `QQ_LOGIN_001` |
| 2 | 用例标题 | 体现测试条件、动作或目标，避免只写“测试登录” |
| 3 | 项目/模块 | 标明属于哪个项目、功能或业务模块 |
| 4 | 优先级 | 常用 P0-P4，P0 通常表示最重要的核心用例 |
| 5 | 前置条件 | 执行前必须满足的环境、账号、权限和数据条件；没有前置条件时可不填 |
| 6 | 测试步骤 | 按执行顺序写清页面路径、输入、点击或接口调用 |
| 7 | 测试数据 | 步骤中使用的关键账号、参数、文件、订单号或边界值 |
| 8 | 预期结果 | 写可观察、可判定的结果，必要时同时验证页面、接口和数据库 |

企业模板还可能增加需求编号、测试类型、设计人、执行人、执行日期、实际结果、测试环境、附件、缺陷编号和自动化标记。字段多少不是重点，重点是支持协作与追溯。

### 用例编号和需求追踪

建议编号在整个项目中保持唯一，例如：

```text
SHOP_LOGIN_001
SHOP_ORDER_015
PAY_REFUND_003
```

如果团队有需求编号，可以建立以下追踪关系：

```text
需求 REQ-LOGIN-01
  -> 测试点 TP-LOGIN-03
  -> 用例 SHOP_LOGIN_005
  -> 执行记录
  -> 缺陷 BUG-1024
  -> 修复验证与回归结果
```

这条链路可以回答“需求是否测过”“这个缺陷影响哪条需求”“修复后是否回归”等项目问题。

## 1-3.3 用例编写规范

### 标题规范

不推荐：`测试密码框`。

推荐：`密码为空时点击登录，页面阻止提交并提示“密码不能为空”`。

标题最好包含条件、动作和验证目标，让执行者不用打开全部步骤就能理解用例意图。

### 步骤规范

步骤只描述执行动作，不要把预期结果混在动作里。例如：

1. 打开 QQ 登录页面；
2. 在账号框输入已注册账号；
3. 在密码框输入错误密码；
4. 点击“登录”。

不要写成“输入正确账号，登录成功”，因为“正确”和“成功”没有给出可执行标准。

### 预期结果规范

预期结果必须可观察、可判断。例如：

- 页面显示“密码不正确”；
- 登录按钮保持可用或进入加载状态；
- 接口返回 HTTP 200，业务码为登录失败；
- 数据库不新增订单；
- 失败次数增加 1，达到阈值后账号锁定。

### 页面、接口、数据库三层预期

对于重要业务，最好不要只写页面结果，可以分层描述：

1. **页面层**：按钮状态、提示文案、页面跳转、列表展示；
2. **接口层**：HTTP 状态码、业务码、响应字段、错误信息和耗时；
3. **数据层**：订单状态、库存数量、用户状态、流水记录和日志。

例如支付成功的预期可以写成：页面显示支付成功并跳转订单详情；支付接口返回成功业务码；订单状态变为已支付；支付流水新增且金额与订单一致。分层预期有助于判断问题到底在前端、接口服务还是数据处理。

## 1-3.5 设计用例时如何避免穷举

当输入空间很大时，不可能把每一个值都测试一遍。常用的设计方法包括：

1. **等价类划分法**：按相同特征把输入划分为有效和无效集合，每类选择代表值；
2. **边界值分析法**：重点选择边界、刚好小于边界、刚好大于边界的值；
3. **场景法**：按完整业务流程设计正常、异常和替代场景；
4. **错误推断法**：结合经验猜测高风险输入和容易出错的操作；
5. **因果图法、判定表法**：适合多个条件组合导致不同结果的场景；
6. **正交实验法**：在多个因素和取值较多时，用较少组合覆盖主要交互影响。

本章课件/XMind 明确列出等价类及用例设计步骤；已有可读取的课程转写还出现了边界值和场景法讲解片段。由于这些转写文件没有和 9 个 MP4 完成逐文件绑定，本文把它们作为本章相关的设计方法补充，而没有伪造具体视频编号。

### 等价类划分步骤

1. 明确需求和输入规则；
2. 找出划分维度，例如长度、类型、范围、格式和业务规则；
3. 划分有效等价类和无效等价类；
4. 为每个等价类选择代表数据；
5. 编写用例并检查是否覆盖需求。

### 边界值基本思路

对于允许范围 `6-18`，不要只测一个中间值。应重点考虑：

- `5`：刚好小于下边界；
- `6`：下边界；
- `7`：刚好大于下边界；
- `17`：刚好小于上边界；
- `18`：上边界；
- `19`：刚好大于上边界。

### 场景法基本思路

场景法关注业务流程，而不只是某个输入框。例如电商流程可以拆成：注册 → 登录 → 选商品 → 加购物车 → 下单 → 支付 → 发货 → 收货。除了正常流程，还要补充库存不足、支付失败、优惠券失效、重复提交、取消订单和退款等异常分支。

## 1-3.7 就业补充：用例和测试点的区别

- **测试点**是“要验证什么”，例如“密码为空时不能登录”；
- **测试用例**是“如何验证”，包括前置条件、步骤、数据和预期结果。

一个测试点可以拆成多条用例。例如“密码长度符合规则”可以设计为空、最小长度、最大长度、超过最大长度、包含非法字符等多条用例。

## 1-3.8 就业补充：用例优先级建议

- **P0**：核心主流程、资金、登录、权限、数据安全、冒烟必测；
- **P1**：常见正常流程和高频异常流程；
- **P2**：一般异常、低频功能和常规兼容性；
- **P3/P4**：低风险体验细节或特殊组合，按时间安排执行。

具体 P0-P4 定义以团队规范为准。不要把用例优先级和 Bug 严重程度混为一谈。

## 1-3.9 本节练习与答案

### 练习 1：把“测试密码框”改成可执行标题。

**答案**：`密码为空时点击登录，页面阻止提交并提示密码不能为空`。

### 练习 2：下面的用例有什么问题？

```text
步骤：输入正确数据，结果正确。
```

**答案**：入口、账号、数据、动作和“正确”都没有定义，无法执行和判断。应写明页面路径、具体输入、点击动作，以及页面、接口和数据层的可观察结果。

### 练习 3：账号允许 6-10 位自然数，请至少设计哪些代表数据？

**答案**：至少包括有效值 `8 位自然数`，无效值 `4 位自然数`、`12 位自然数` 和 `8 位非自然数`。进一步做边界值时可选择 `5、6、7、9、10、11` 位等代表数据。

### 练习 4：为什么不能把“登录成功、错误密码、多浏览器兼容”写成一条用例？

**答案**：它们属于不同风险和不同验证目标。混在一起会造成执行结果不清楚、缺陷归因困难、回归范围不明确，应该拆成成功流程、错误密码和兼容性等独立用例。

# 二、章节综合复习

## 2.1 高频易错点

1. **功能测试不等于黑盒测试**：功能测试说明测什么，黑盒测试说明是否依赖内部实现；
2. **自动化测试不是测试类型的全部**：它通常是执行手段，需要建立在明确需求和断言之上；
3. **测试流程不是开发完成后才开始**：需求评审阶段就应参与并发现风险；
4. **测试用例不是越多越好**：应优先覆盖风险，使用等价类和边界值减少重复；
5. **用例优先级不等于缺陷严重程度**；
6. **通过率高不等于可以发布**：还要看阻塞性缺陷、未覆盖风险和环境限制；
7. **测试报告不是简单统计数字**：必须说明范围、版本、证据、遗留风险和结论；
8. **“页面显示成功”不代表业务真的成功**：必要时要核对接口响应、数据库和日志。

## 2.2 章节综合题与答案

### 综合题 1

**题目**：请说明“普通用户在 Chrome 浏览器中使用错误密码登录”至少可以从哪些维度分类。

**答案**：

- 按阶段：系统测试；
- 按代码可见度：黑盒测试；
- 按执行方式：动态测试；
- 按内容：功能测试、兼容性测试（如果重点比较 Chrome 与其他浏览器）；
- 按流程性质：异常流程测试；
- 如果同时验证账号锁定、鉴权和会话，还涉及安全测试。

### 综合题 2

**题目**：需求变更为“登录增加验证码”，测试应如何安排？

**答案**：先在需求评审中确认验证码的生成、有效期、错误次数、刷新、重复使用和异常提示规则；再更新测试点和用例。除登录成功外，还应回归验证码错误、过期、为空、重复使用、刷新、找回密码、注册、第三方登录、锁定策略、接口调用方和核心冒烟流程。范围根据变更影响分析决定。

### 综合题 3

**题目**：测试发现需求“用户可以快速登录”无法测量，应如何处理？

**答案**：提出可量化的验收标准，例如指定网络、设备、数据量和并发条件，明确 P95 响应时间、成功率和超时处理。未确认前将其记录为需求风险，不自行设定最终标准。

### 综合题 4

**题目**：请写出一条规范缺陷的基本内容。

**答案**：至少包含缺陷标题、发现版本、测试环境、前置条件、复现步骤、实际结果、预期结果、严重程度/优先级、复现频率、附件证据和相关用例编号。例如：

## 3.2 参考答案：QQ 登录测试点

下面是一组可以直接用于练习或面试展示的测试点：

1. 输入正确账号和正确密码，登录成功；
2. 账号为空，点击登录时给出必填提示；
3. 密码为空，点击登录时给出必填提示；

12. 退出登录后使用浏览器后退不能访问受保护页面；
13. 登录请求重复提交不会创建多个会话；
14. 在 Chrome、Edge 等目标浏览器中登录行为一致；
15. 网络断开或服务异常时给出可理解的错误提示，不能展示错误堆栈。

## 3.6 验收标准

- 别人拿到用例后可以不询问你就执行；
- 每条用例的预期结果可以明确判断通过或失败；
- 测试数据和前置条件足以复现；
- 每条需求或测试点都能找到对应的用例；
- 发现问题时有完整证据，而不是只描述主观感受；
- 能解释为什么选择这些测试数据和优先级；
- 能针对测试结果给出清晰的通过、暂缓发布或有条件发布结论。
