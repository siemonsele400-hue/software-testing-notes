# 阶段一：测试基础

## 第四章：Web 测试

本章解决一个核心问题：**面对浏览器、页面、接口、会话、数据和多种终端组成的 Web 系统，如何识别测试范围、设计测试点、执行测试并定位问题。**

前三章分别建立了测试基础、用例设计方法和缺陷管理能力。本章把这些能力放到 Web 项目中，帮助你形成一套完整的 Web 功能测试思路，并为后续接口测试、数据库和自动化学习打基础。

> 本章中的示例规则是学习用假设，实际项目应以需求、原型、接口文档和产品确认结果为准。未明确的规则不能由测试人员自行臆造。

# 4-1 Web 测试基础

## 4-1.1 视频原讲提炼

Web 测试的重点不是“把网页所有按钮点一遍”，而是验证用户通过浏览器访问系统时，页面、请求、服务、数据和外部依赖能否共同完成业务。

学习 Web 测试时应建立以下观察顺序：

```text
用户操作
  -> 浏览器页面和 JavaScript
  -> HTTP 请求
  -> 服务端业务处理
  -> 数据库、缓存或第三方服务
  -> HTTP 响应
  -> 页面展示和数据更新
```

因此，一个“点击保存没有成功”的现象，可能来自：

- 前端按钮没有触发事件；
- 请求没有发送或请求参数错误；
- 接口返回错误码；
- 服务端处理失败；
- 数据库写入失败；
- 接口已经成功，但页面没有刷新；
- 页面读取了缓存中的旧数据。

测试人员需要先确认现象，再结合网络请求、响应、控制台和数据状态缩小范围。

## 4-1.2 Web 系统的基本组成

### 浏览器

浏览器负责加载 HTML、CSS、JavaScript 和图片等资源，并执行用户操作。常见测试对象包括：

- 页面是否正常加载；
- 元素是否显示、可点击和可输入；
- 表单校验是否正确；
- 页面跳转和刷新是否正确；
- 浏览器缓存、Cookie 和本地存储是否影响结果；
- 控制台是否出现错误。

### 前端

前端负责页面展示、交互、部分校验和接口调用。前端校验可以改善用户体验，但不能代替服务端校验，因为用户可以绕过页面直接发送请求。

### 接口和服务端

接口负责接收请求、执行业务规则、访问数据并返回结果。测试人员需要关注：

- 请求方法和 URL；
- 参数名称、类型、必填和默认值；
- 身份认证和权限；
- HTTP 状态码与业务码；
- 响应字段、数据类型和错误信息；
- 重复请求、超时、重试和幂等性。

### 数据库、缓存和第三方服务

页面显示正确不代表数据一定正确。重要业务需要检查：

- 数据是否正确新增、修改和删除；
- 事务失败后是否回滚；
- 缓存是否及时更新；
- 消息和异步任务是否重复执行；
- 第三方支付、短信、地图或登录服务失败时系统如何处理。

## 4-1.3 页面、接口和数据三层验证

对重要功能，建议至少从三层验证：

| 层次 | 重点检查 | 示例 |
| --- | --- | --- |
| 页面层 | 展示、按钮、提示、跳转和状态 | 保存后页面显示“保存成功” |
| 接口层 | 请求、状态码、业务码和响应字段 | 返回 HTTP 200，业务码为 `SUCCESS` |
| 数据层 | 数据新增、更新、删除和一致性 | 用户昵称在用户表中正确更新 |

三层结果不一致时，要记录每一层的现象。例如页面显示成功但接口实际返回失败，或者接口返回成功但数据库没有数据，这些都可能是不同层面的缺陷。

## 4-1.4 Web 测试与桌面测试的差异

| 对比项 | Web 测试 | 桌面应用测试 |
| --- | --- | --- |
| 访问方式 | 浏览器和 URL | 安装后的本地程序 |
| 环境影响 | 浏览器、网络、缓存、Cookie、设备 | 操作系统、安装包、本地权限 |
| 发布方式 | 服务端部署后用户访问 | 客户端安装或升级 |
| 重点风险 | 会话、兼容性、接口、权限、网络 | 安装卸载、文件、进程、本地资源 |
| 常见证据 | 网络请求、控制台、页面截图 | 日志、进程、文件和系统事件 |

这并不意味着 Web 测试不需要测试安装、系统和性能，而是测试重点不同。

## 4-1.5 就业补充：Web 测试人员的基本工具

初级功能测试岗位常用工具包括：

- 浏览器开发者工具：查看 Elements、Console、Network、Application；
- 接口工具：Postman、Apifox 或其他团队工具；
- 缺陷和用例工具：禅道、Jira、Azure DevOps；
- 数据库工具：DBeaver、Navicat 或命令行客户端；
- 抓包工具：Charles、Fiddler、mitmproxy；
- 页面与接口自动化工具：Selenium、Playwright、Requests、Pytest。

工具名称不是能力本身。面试时应说明你用工具解决了什么问题、保留了什么证据、如何判断结果。

## 4-1.6 本节练习与答案

### 练习 1：页面显示保存成功，数据库没有记录，属于什么问题？

**答案**：这是页面、接口和数据结果不一致的问题，通常应作为功能或数据一致性缺陷处理。提交前需要确认接口响应、数据库查询时间、事务状态和缓存影响，不能只凭页面现象猜测根因。

### 练习 2：为什么不能只测试前端输入校验？

**答案**：用户可以绕过页面直接调用接口。如果服务端没有再次校验，非法数据可能仍然写入系统，造成数据、权限或安全风险。

### 练习 3：点击按钮没有反应，第一步应看什么？

**答案**：先确认页面是否真的触发了请求，再查看 Console 是否有 JavaScript 错误、Network 是否有失败请求，并确认按钮是否被禁用、是否存在前置校验或遮挡。

# 4-2 HTTP 与浏览器基础

## 4-2.1 URL 组成

URL 通常可以拆分为：

```text
https://example.com:443/user/profile?id=1001#security
```

| 部分 | 示例 | 说明 |
| --- | --- | --- |
| 协议 | `https` | 客户端与服务端通信方式 |
| 域名 | `example.com` | 服务地址 |
| 端口 | `443` | 服务监听端口，默认端口有时可省略 |
| 路径 | `/user/profile` | 访问的资源或接口路径 |
| 查询参数 | `id=1001` | 传递查询条件 |
| 片段 | `#security` | 浏览器端页面位置，通常不发送给服务端 |

测试时需要确认路径、参数编码、大小写、特殊字符和缺少参数时的行为。

## 4-2.2 常见 HTTP 方法

| 方法 | 常见用途 | 测试关注点 |
| --- | --- | --- |
| GET | 查询资源 | 参数、分页、过滤、缓存和是否产生副作用 |
| POST | 创建资源或提交动作 | 必填参数、重复提交、幂等和错误处理 |
| PUT | 整体更新资源 | 是否覆盖未传字段、权限和版本冲突 |
| PATCH | 部分更新资源 | 只更新指定字段，其他字段是否保持 |
| DELETE | 删除资源 | 权限、重复删除、软删除和关联数据 |

实际项目中方法的使用可能受团队接口规范影响，不能只凭方法名称判断业务行为。

## 4-2.3 HTTP 状态码

| 类别 | 常见状态码 | 一般含义 |
| --- | --- | --- |
| 2xx | 200、201、204 | 请求成功或资源创建成功 |
| 3xx | 301、302、304 | 重定向或缓存相关 |
| 4xx | 400、401、403、404、409、429 | 请求错误、未认证、无权限、资源不存在、冲突或限流 |
| 5xx | 500、502、503、504 | 服务端异常、网关异常、服务不可用或超时 |

状态码不能完全代替业务码。例如登录失败可能返回 HTTP 200，但业务码为 `INVALID_PASSWORD`；也可能返回 HTTP 401。测试人员应根据接口契约判断是否正确，不能机械地把所有 200 都当作成功。

## 4-2.4 请求和响应的主要组成

### 请求

- 请求方法和 URL；
- Query 参数；
- Path 参数；
- Headers；
- Cookie；
- Request Body；
- Token 或其他认证信息。

### 响应

- HTTP 状态码；
- Response Headers；
- Set-Cookie；
- JSON、HTML 或文件响应体；
- 响应时间和大小；
- 错误信息与业务码。

## 4-2.5 Cookie、Session、Token 和本地存储

### Cookie

Cookie 通常由浏览器保存并在符合域名、路径和安全规则时自动发送。测试需要关注：

- 登录后是否生成会话 Cookie；
- 退出后 Cookie 是否失效或被清除；
- Cookie 的 `Secure`、`HttpOnly`、`SameSite` 属性是否符合要求；
- 跨域和子域场景是否符合设计。

### Session

Session 是服务端保存的会话信息，浏览器通常通过 Session ID 关联到服务端状态。需要验证超时、退出、并发登录和会话固定等风险。

### Token

Token 通常由客户端保存并在请求头中发送，例如：

```text
Authorization: Bearer <token>
```

需要测试 Token 缺失、过期、篡改、权限变化、退出后继续使用和跨用户访问。

### Local Storage 与 Session Storage

- Local Storage 通常长期保留，除非主动清除；
- Session Storage 通常与当前标签页会话相关；
- 不应在浏览器存储中明文保存不必要的敏感数据。

## 4-2.6 浏览器开发者工具的使用

### Elements

用于查看页面结构、元素属性、样式和是否被遮挡。修改 Elements 中的内容只改变本地页面，不代表服务端数据已经改变。

### Console

用于查看 JavaScript 错误、警告和调试信息。Console 没有报错也不代表业务正确，还要看请求和数据。

### Network

最重要的排查面板之一。可以查看：

- 请求是否发出；
- 请求方法和 URL；
- 请求参数和请求头；
- 状态码和响应体；
- 请求耗时；
- 重定向和失败原因；
- 是否存在重复请求。

### Application

用于检查 Cookie、Local Storage、Session Storage、缓存、Service Worker 等浏览器端数据。

## 4-2.7 本节练习与答案

### 练习 1：登录失败返回 HTTP 200，是否一定错误？

**答案**：不一定。要根据接口契约判断。如果团队约定业务失败统一用 HTTP 200 加业务码，那么可以是正确设计；如果约定认证失败必须返回 401，则是接口缺陷。

### 练习 2：退出登录后再次访问个人中心仍能看到数据，应检查哪些内容？

**答案**：检查页面缓存、浏览器后退缓存、Cookie/Token 是否失效、接口是否仍返回数据、服务端是否验证会话和权限，以及个人数据是否通过其他接口泄露。

### 练习 3：Network 中发现一次点击发送了两次相同请求，可能有什么风险？

**答案**：可能造成重复创建、重复扣款、重复发送短信、库存重复扣减或重复写入日志。应结合接口副作用、幂等设计和数据库结果判断。

# 4-3 Web 功能测试

## 4-3.1 页面和导航测试

### 页面加载

- 页面 URL 是否正确；
- 首屏关键内容是否出现；
- 空数据、加载中、加载失败和重试状态是否清晰；
- 刷新页面后状态是否符合需求；
- 直接输入深层 URL 时是否能正确处理；
- 前进、后退、重复打开标签页是否影响数据。

### 链接和按钮

- 链接目标是否正确；
- 新窗口或当前窗口行为是否符合需求；
- 按钮是否可用、禁用和加载中状态是否正确；
- 快速连续点击是否重复提交；
- 无权限用户是否看到或可以调用该按钮；
- 操作成功、失败和超时后按钮状态是否恢复。

### 表单

- 必填、非必填、默认值和占位符；
- 长度、格式、范围和特殊字符；
- 空值、空格、前后空格和复制粘贴；
- 错误提示、焦点位置和错误字段高亮；
- Tab 顺序和回车提交；
- 校验发生在输入时、失焦时还是提交时；
- 提交失败后已输入内容是否保留。

## 4-3.2 登录测试

登录是 Web 测试中的核心入口，至少覆盖：

| 维度 | 典型测试点 |
| --- | --- |
| 正常流程 | 正确账号和密码登录成功 |
| 输入校验 | 账号为空、密码为空、格式错误、超长 |
| 账号状态 | 未注册、已锁定、已注销、被冻结 |
| 密码策略 | 错误密码、连续错误、大小写、前后空格 |
| 验证码 | 正确、错误、过期、刷新、重复使用 |
| 会话 | 登录后访问受保护页面、刷新、退出、超时 |
| 权限 | 普通用户、管理员、不同租户和不同数据范围 |
| 异常 | 网络断开、接口 500、超时、重复点击 |
| 兼容性 | 目标浏览器、设备、分辨率和缩放比例 |

## 4-3.3 注册测试

注册通常涉及手机号/邮箱、密码、验证码、协议和账号唯一性：

- 手机号或邮箱格式及长度边界；
- 已注册账号不能重复创建；
- 密码复杂度和两次输入一致性；
- 图片验证码、短信验证码或邮箱验证码；
- 验证码有效期、刷新、重试和发送频率；
- 未同意协议不能提交；
- 连续点击不能创建多个账号；
- 注册成功后的跳转和账号状态；
- 失败后输入内容、验证码和按钮状态；
- 接口直接提交非法数据不能绕过页面规则。

## 4-3.4 搜索和列表测试

### 搜索

- 精确、模糊、大小写、中文和特殊字符；
- 空搜索、超长搜索和不存在关键词；
- 前后空格和多关键词；
- 搜索结果数量、排序和高亮；
- 分页、翻页、最后一页和无结果；
- 快速连续搜索是否出现旧结果覆盖新结果；
- 网络慢时是否显示加载状态；
- 搜索条件返回列表页后是否保留。

### 列表

- 数据为空、1 条、最大分页数量；
- 排序升序、降序和默认顺序；
- 列表字段、金额、日期和时区；
- 选择、批量操作和全选状态；
- 删除、导出和权限控制；
- 刷新后数据是否一致；
- 同一数据被其他用户修改或删除后的处理。

## 4-3.5 文件上传和下载

### 上传

- 支持和不支持的文件类型；
- 空文件、最小文件、最大文件和超限文件；
- 中文名、特殊字符名、重复文件名；
- 文件内容与扩展名不一致；
- 上传中取消、网络中断和重复上传；
- 无权限用户是否可以上传；
- 上传后文件是否可访问、可预览和可下载；
- 文件名、路径和内容是否存在安全风险。

### 下载

- 下载文件内容、名称和扩展名；
- 断点续传和大文件；
- 无权限下载他人文件；
- 文件已删除或过期后的提示；
- 下载接口是否泄露服务器真实路径。

## 4-3.6 购物车和下单测试

- 加购、减少、增加、删除和清空；
- 库存为 0、库存为 1、库存变化；
- 价格、优惠、运费和总金额计算；
- 商品下架、价格变化和失效优惠券；
- 未登录加购后登录是否保留；
- 多标签页或多个设备同时修改购物车；
- 重复提交订单和支付；
- 支付成功、失败、取消、超时和回调重复；
- 订单、库存、优惠券和支付流水的一致性。

## 4-3.7 常见 Web 状态

页面并不只有“成功”和“失败”，还应覆盖：

```text
初始
  -> 加载中
  -> 加载成功
  -> 加载失败
  -> 空数据
  -> 提交中
  -> 提交成功
  -> 提交失败
  -> 无权限
  -> 会话过期
```

很多缺陷来自状态切换遗漏，例如失败后按钮一直处于加载中、空列表没有空状态、登录过期后页面仍允许提交。

## 4-3.8 本节练习与答案

### 练习 1：登录成功后刷新页面，至少验证什么？

**答案**：验证会话是否保持、用户信息是否正确、受保护接口是否仍可访问、页面是否重复发起登录请求、刷新后是否出现旧数据或权限错误。

### 练习 2：搜索输入“空格”，应该预期什么？

**答案**：不能直接猜。需要根据需求确认是去除首尾空格后搜索、视为空搜索、按空格作为合法关键词，还是提示不能为空。确认后再编写可判断的预期结果。

### 练习 3：商品详情页显示库存 1，同时两个用户下单，应该如何测试？

**答案**：设计并发或交错操作，验证最多一个订单成功扣减最后库存，另一个用户得到明确提示；同时核对订单、库存、支付和日志，防止超卖或扣库存不一致。

# 4-4 Web 兼容性、易用性与安全测试

## 4-4.1 兼容性测试

兼容性测试不是“所有浏览器都测一遍”，而是根据用户分布、业务风险和支持范围建立测试矩阵。

### 浏览器维度

- Chrome、Edge、Firefox、Safari；
- 目标浏览器的支持版本；
- 内核差异和浏览器隐私策略；
- Cookie、缓存、文件下载和权限行为。

### 操作系统和设备

- Windows、macOS；
- Android、iOS；
- 手机、平板、桌面显示器；
- 横屏、竖屏、不同像素密度和缩放比例。

### 网络维度

- 正常网络；
- 高延迟、低带宽；
- 网络断开和恢复；
- 请求超时、重复重试和弱网下的页面状态。

### 兼容性测试矩阵示例

| 浏览器 | 系统/设备 | 分辨率 | 重点功能 | 结果 |
| --- | --- | --- | --- | --- |
| Chrome | Windows | 1920×1080 | 登录、搜索、下单 | 待执行 |
| Edge | Windows | 1366×768 | 登录、搜索 | 待执行 |
| Safari | iPhone | 390×844 | 注册、支付 | 待执行 |
| Chrome | Android | 412×915 | 注册、购物车 | 待执行 |

优先级应根据真实用户比例和核心业务确定，而不是平均分配时间。

## 4-4.2 响应式和移动端 Web

- 页面宽度变化时是否出现横向滚动；
- 内容、按钮、弹窗和键盘是否重叠；
- 点击区域是否足够；
- 输入框获得焦点后页面是否滚动到可见区域；
- 返回、刷新和系统手势是否破坏表单数据；
- 图片、表格和长文本是否适配；
- 移动网络下加载和错误提示是否可理解。

## 4-4.3 易用性测试

- 用户是否理解页面标题、按钮和提示；
- 错误提示是否说明问题和解决办法；
- 关键操作是否有明确反馈；
- 误操作是否可以取消或恢复；
- 表单顺序、焦点和键盘操作是否合理；
- 信息层级和视觉对比是否足够；
- 无障碍用户能否使用键盘、屏幕阅读器或放大功能完成核心流程。

易用性问题也要有可复现条件和具体影响，不要只写“感觉不好用”。

## 4-4.4 Web 安全基础测试

本节只建立测试意识，不替代专业安全测试。所有测试必须在授权的测试环境执行。

### 认证

- 未登录访问受保护页面和接口；
- Token 或 Cookie 缺失、过期、篡改；
- 退出后旧会话是否失效；
- 多设备登录和会话管理；
- 登录失败次数和验证码策略。

### 授权

- 普通用户访问管理员页面；
- 用户 A 访问用户 B 的订单、文件或地址；
- 修改 URL、请求参数或资源 ID 后是否越权；
- 前端隐藏按钮后，接口是否仍能被调用；
- 不同租户之间是否隔离数据。

### 输入和输出

- 输入框、搜索框、文件上传和接口参数的非法输入；
- 页面是否原样输出用户输入；
- 错误页面是否泄露堆栈、路径、Token 或内部服务信息；
- 敏感数据是否在页面、日志、URL、响应和浏览器存储中暴露。

### 业务安全

- 重复提交、重放请求、优惠券重复使用；
- 修改金额、用户 ID、订单 ID 或权限字段；
- 验证码绕过、频率限制绕过；
- 未授权下载和批量查询。

发现高风险安全问题时，应按项目安全流程单独升级，不要把真实敏感数据放进普通缺陷附件。

## 4-4.5 本节练习与答案

### 练习 1：页面隐藏了管理员按钮，普通用户是否就安全了？

**答案**：不安全。隐藏按钮只是前端展示控制，普通用户仍可能直接调用接口。必须验证服务端身份认证、权限判断和数据范围。

### 练习 2：兼容性测试如何确定浏览器组合？

**答案**：根据产品支持范围、用户访问数据、业务关键程度和浏览器差异确定优先级。先覆盖核心用户和高风险功能，再安排低占比组合。

### 练习 3：错误提示显示完整 Java 异常堆栈，属于什么问题？

**答案**：属于安全和易用性问题。它可能泄露内部路径、类名、数据库或服务信息，也会让用户无法理解如何处理。应保留脱敏证据并按安全流程处理。

# 4-5 Web 性能与异常场景

## 4-5.1 Web 性能测试关注什么

本章不展开性能工具操作，但功能测试人员应知道常见指标：

- 响应时间：请求从发出到收到结果所需时间；
- 吞吐量：单位时间内处理的请求或业务数；
- 并发用户数：同时发起或保持操作的用户规模；
- 错误率：失败请求占总请求的比例；
- 资源使用：CPU、内存、磁盘、网络和数据库连接；
- 稳定性：持续运行时是否出现性能下降、错误堆积或资源泄漏。

“页面加载快”不是可执行标准。应明确网络、设备、数据规模、并发量和目标指标，例如“在指定环境和并发条件下，核心接口 P95 响应时间不超过某个值”。

## 4-5.2 功能测试中的性能观察点

即使没有进行正式压测，也应留意：

- 页面是否长时间无反馈；
- 点击一次是否发起大量重复请求；
- 列表数据量增加后是否明显变慢；
- 大图片、大文件和复杂表格是否阻塞页面；
- 分页是否真正限制了查询数据量；
- 接口失败后是否无限重试；
- 弱网下是否出现重复提交或状态错乱。

发现性能现象时，应记录数据量、网络、设备、浏览器、响应时间和请求数量，避免只写“很慢”。

## 4-5.3 异常场景设计

Web 系统常见异常包括：

| 异常 | 需要观察 |
| --- | --- |
| 网络断开 | 页面提示、数据保存、重试和恢复 |
| 请求超时 | 是否重复提交、是否可取消、状态是否明确 |
| 服务返回 500 | 用户提示、日志、按钮状态和数据回滚 |
| 第三方服务失败 | 降级、补偿、重试和人工处理 |
| 浏览器刷新 | 表单、订单和支付状态是否一致 |
| 多标签页 | 登录、权限和数据更新是否正确 |
| 并发操作 | 是否重复创建、超卖、覆盖他人修改 |
| 服务重启 | 已提交业务是否可恢复，数据是否丢失 |

## 4-5.4 本节练习与答案

### 练习 1：如何把“页面加载要快”转成测试条件？

**答案**：明确页面、网络、设备、数据量、并发、统计指标和时间限制。例如指定“测试环境、Chrome、固定数据量和并发条件下，首页首屏可交互时间和接口 P95 响应时间应满足约定阈值”。具体阈值必须由产品或项目确认。

### 练习 2：支付接口超时后用户再次点击支付，重点验证什么？

**答案**：验证是否重复扣款、是否创建重复支付流水、订单状态是否最终一致、重试是否幂等、页面是否明确提示处理中或可查询结果。

# 4-6 Web 测试流程与证据

## 4-6.1 测试准备

执行前确认：

- 需求、原型、接口文档和验收标准；
- 测试范围和不在范围内的内容；
- 构建版本、部署时间和环境地址；
- 浏览器、设备和系统版本；
- 测试账号、角色、租户和数据；
- 第三方服务、短信、支付和邮件是否可用；
- 已知问题、限制和回滚方案。

## 4-6.2 冒烟测试

Web 版本冒烟可以包含：

- 首页和核心页面可访问；
- 用户可以登录和退出；
- 关键接口返回符合契约；
- 核心查询和保存可以完成；
- 一个最小业务链路可以闭环；
- 数据库、缓存和必要依赖可用。

冒烟失败时，先提交阻塞问题并确认版本是否退回，不要在基础环境不可用时继续执行大量详细用例。

## 4-6.3 测试执行

推荐顺序：

```text
冒烟
  -> 核心主流程
  -> 需求功能和异常流程
  -> 边界与组合
  -> 兼容性
  -> 安全风险
  -> 回归与探索性测试
```

每条用例至少记录：

- 执行版本和环境；
- 用例状态；
- 实际结果；
- 缺陷编号；
- 截图、请求、响应和日志等证据；
- 阻塞原因或未执行原因。

## 4-6.4 Web 问题定位顺序

遇到问题时，可按以下顺序排查：

1. 是否能稳定复现；
2. 页面是否有明显错误；
3. Console 是否有 JavaScript 报错；
4. Network 是否发出请求；
5. 请求方法、URL、参数和认证信息是否正确；
6. 响应状态码、业务码和响应体是否符合预期；
7. 页面是否正确处理响应；
8. 数据库、缓存、消息和日志是否一致；
9. 是否只在某浏览器、设备、账号或网络出现；
10. 补充最小复现步骤和证据后提交缺陷。

不要一开始就断言“后端有问题”或“数据库错了”。测试报告应区分观察到的事实与尚未验证的推测。

## 4-6.5 Web 缺陷示例

```text
标题：退出登录后使用浏览器后退仍可查看用户订单
模块：用户中心 / 会话管理
版本环境：v1.0.4 / QA / Chrome / Windows
严重程度：S1
优先级：P0
前置条件：账号已登录并存在订单，订单列表已加载。
步骤：
1. 点击“退出登录”。
2. 使用浏览器后退返回订单列表。
3. 刷新页面并观察网络请求。
预期结果：会话失效，页面跳转登录页，订单接口返回未授权，不展示个人订单。
实际结果：页面仍展示订单，刷新时订单接口返回 HTTP 200。
证据：录屏、Network 请求、响应体和账号角色。
```

## 4-6.6 测试报告中的 Web 信息

测试总结应说明：

- 测试版本、环境、浏览器和设备；
- 测试范围、未覆盖范围和限制；
- 用例设计、执行、通过、失败和阻塞数量；
- 缺陷按严重程度、优先级和模块的分布；
- 页面、接口、数据和第三方依赖的风险；
- 兼容性和安全测试是否完成；
- 遗留问题、规避方案和发布建议。

## 4-6.7 本节练习与答案

### 练习 1：接口返回成功但页面显示失败，缺陷怎么写？

**答案**：分别记录接口实际响应和页面实际展示，明确需求要求的页面结果。标题可以写“保存接口返回成功后页面仍提示保存失败”，并附 Network 响应和页面截图，不要直接推断是前端代码某一行出错。

### 练习 2：某功能只在 Safari 失败，应如何记录？

**答案**：在标题和环境中明确 Safari 版本、设备、系统、复现概率和对比浏览器结果；同时保留 Console、Network 和页面证据，判断是浏览器兼容、服务端 User-Agent 分支还是设备能力差异。

# 二、章节综合复习

## 4.7 Web 测试维度对照表

| 维度 | 主要问题 | 典型方法/证据 |
| --- | --- | --- |
| 功能 | 需求和业务流程是否正确 | 用例、页面、接口、数据库 |
| 界面 | 页面是否可见、可用、易理解 | 截图、交互步骤、响应式矩阵 |
| 会话 | 登录、退出、超时和权限是否正确 | Cookie、Token、Network |
| 数据 | 页面、接口和存储是否一致 | SQL、响应体、日志 |
| 兼容 | 不同浏览器、设备和网络是否正常 | 兼容性矩阵、录屏 |
| 安全 | 是否存在认证、授权和敏感数据风险 | 角色账号、请求修改、脱敏证据 |
| 性能 | 响应、吞吐和资源是否满足目标 | 指标、时间、请求数、监控 |
| 异常恢复 | 失败、超时、重试和恢复是否正确 | 模拟异常、状态记录、日志 |

## 4.8 高频易错点

1. **Web 测试不等于页面点击测试**：必须关注接口、会话、数据和依赖。
2. **前端校验不等于安全校验**：服务端必须重新验证输入和权限。
3. **HTTP 200 不等于业务成功**：还要检查业务码和响应内容。
4. **接口成功不等于页面正确**：页面可能没有正确处理响应。
5. **隐藏按钮不等于无权限**：必须验证接口不能被越权调用。
6. **刷新和后退不是普通操作**：它们经常暴露会话、缓存和状态问题。
7. **兼容性不是平均测试所有组合**：应依据用户和风险建立矩阵。
8. **性能问题不能只写“很慢”**：需要记录条件、时间、数据量和指标。
9. **重测不等于回归**：修复后要检查相关业务和共享组件。
10. **日志和截图需要脱敏**：不能把真实密码、Token 和生产数据上传到缺陷工具。

## 4.9 综合题与答案

### 综合题 1

**题目**：用户点击登录后页面没有跳转，但 Network 显示接口返回 HTTP 200，响应业务码为 `SUCCESS`。请列出排查方向。

**答案**：

1. 查看响应字段是否完整，Token 或用户信息是否存在；
2. 检查 Console 是否有 JavaScript 错误；
3. 检查前端是否正确读取业务码和跳转字段；
4. 检查 Cookie/Token 是否成功写入；
5. 检查跳转地址是否配置错误或被路由拦截；
6. 检查页面是否仍处于提交中或被弹窗遮挡；
7. 在其他浏览器和账号下复现，区分环境和数据问题。

### 综合题 2

**题目**：普通用户修改 URL 中的订单 ID 后可以查看其他用户订单，属于哪些测试问题？

**答案**：属于授权和数据隔离缺陷，也可能是对象级权限校验缺失。应使用测试账号验证不同用户、不同租户、不同角色和接口直接访问，记录请求、响应和实际数据范围，并按安全流程升级。

### 综合题 3

**题目**：如何测试“支付成功但浏览器关闭后重新打开页面”的场景？

**答案**：支付请求发出后关闭浏览器，等待支付结果或回调，再重新打开系统并登录，查询订单、支付流水和库存。验证订单最终状态、金额、库存、优惠券、页面提示和重复支付行为是否一致。

### 综合题 4

**题目**：一个列表页面在数据为空时一直显示加载中，如何判断缺陷信息是否完整？

**答案**：需要补充页面入口、账号权限、数据准备、版本环境、操作步骤、实际加载状态、接口响应、预期空状态、复现概率和截图/Network 证据。还要确认接口是否返回空数组、请求是否完成，以及是否只发生在某浏览器或特定查询条件下。

## 4.11 参考答案：测试点

### 登录

2. 手机号为空；

## 4.15 参考答案：3 条规范 Web 缺陷

### 缺陷 1：退出后仍可查看订单

```text
标题：退出登录后访问订单列表接口仍返回当前用户订单
模块：用户中心 / 会话管理
版本环境：v1.0.5 / QA / Chrome / Windows
严重程度：S1；优先级：P0；类型：安全/功能
前置条件：用户已登录并存在订单。
步骤：
1. 进入用户中心订单列表。
2. 点击退出登录。
3. 直接访问订单列表 URL。
4. 查看 Network 中订单接口响应。
预期结果：跳转登录页，订单接口返回未授权，不展示订单数据。
实际结果：页面仍展示订单，接口返回 HTTP 200 和订单数据。
证据：录屏、请求响应和账号角色。
```

### 缺陷 2：第 5 次错误密码后账号未锁定

```text
标题：密码连续错误 5 次后账号仍可继续登录
模块：登录 / 账号安全
版本环境：v1.0.5 / QA
严重程度：S2；优先级：P1；类型：功能/安全
前置条件：账号未锁定，规则为连续错误 5 次锁定 10 分钟。
步骤：
1. 输入正确手机号和错误密码并提交。
2. 连续重复步骤 1 共 5 次。
3. 第 6 次输入正确密码并提交。
预期结果：第 5 次失败后账号锁定 10 分钟，第 6 次不能登录。
实际结果：第 6 次使用正确密码登录成功，账号未锁定。
证据：执行记录、登录接口响应和账号状态。
```

### 缺陷 3：订单接口失败时页面一直加载

```text
标题：订单列表接口返回 503 后页面持续显示加载中且无重试入口
模块：用户中心 / 订单列表

1. 进入用户中心订单列表。
2. 等待接口返回 503。
3. 观察页面状态。

```

## 4.17 页面、接口和数据库联合验证示例

以“修改收货地址”为例：

1. 页面输入新地址并点击保存；
2. Network 确认发送正确的 `PUT` 请求、用户身份和地址字段；
3. 响应确认状态码、业务码和返回地址正确；
4. 数据库确认地址记录更新，旧地址是否按需求保留；
5. 刷新页面、重新登录或从订单页面读取，确认数据仍一致；
6. 使用其他用户账号验证不能访问或修改该地址；
7. 提交缺陷时分别附页面截图、接口响应、SQL 查询结果和请求时间。

## 4.18 面试表达示例

> 我做 Web 测试时不会只看页面。先根据需求拆分正常、异常、边界、会话、权限、兼容性和异常恢复场景，再用浏览器开发者工具确认请求、响应和控制台信息。对登录、注册和订单这类核心功能，我会同时验证页面展示、接口状态和数据库结果。执行顺序是先冒烟，再测核心主流程、异常和边界，最后做兼容性和安全风险检查。发现问题时记录版本、浏览器、账号、步骤、预期和实际结果，并保留截图、Network 和日志证据；修复后先重测原问题，再根据影响范围回归相关功能。
