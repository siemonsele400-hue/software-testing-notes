# 第 08 集：测试用例设计——场景法

> **本集核心**：场景法基于业务流程设计用例。视频以电商“注册 → 登录 → 选商品 → 下单 → 支付 → 确认收货”为例，并强调先获得/绘制业务流程图，再覆盖主流程、异常流程和状态分支。

## 一、场景法解决什么问题

等价类适合一个输入框，场景法适合跨页面、跨服务的业务链路。它验证的是“用户完成一件事的过程是否正确”，包括前一步产生的数据能否被下一步使用、失败后能否恢复、状态是否按规则流转。

## 二、先画流程图

流程图通常由产品或原型提供；没有时，测试人员根据需求补画并请产品确认。常见符号：开始/结束、处理动作、判断分支、连接箭头。图中每个判断都要问：条件是什么、否分支去哪里、是否允许重试或返回。

示例：

```text
注册 → 登录 → 选择商品 → 提交订单
                         ├─ 库存足 → 支付
                         │          ├─ 成功 → 待发货
                         │          └─ 失败 → 待支付/取消
                         └─ 库存不足 → 提示并停留购物车
```

## 三、主流程与异常流程

### 主流程

覆盖最常见、最有业务价值的成功路径：新用户注册成功、登录、下单、支付、收货。主流程通常是高优先级冒烟用例。

### 异常流程

覆盖每个关键节点的失败和恢复：验证码错误、账号锁定、库存不足、优惠券失效、支付超时、重复点击、取消订单、退款和重新支付。异常流程应验证状态没有跳跃，例如支付失败不能变成已发货。

## 四、场景设计步骤

1. 明确角色、入口和业务目标；
2. 获取或绘制流程图；
3. 列出节点、判断和状态；
4. 组合主流程、替代流程和异常流程；
5. 为每个场景写前置数据、步骤、预期和清理动作；
6. 检查跨模块数据、权限、通知和日志。

## 五、与状态迁移的结合

订单可能经历“待支付 → 已支付 → 待发货 → 已发货 → 已完成”，也可能“待支付 → 已取消”或“支付中 → 支付失败”。场景法要验证合法迁移、非法迁移、重复操作和并发操作，而不是只看页面文字。

## 六、示例场景

| 场景 | 关键验证 |
|---|---|
| S1 正常购买 | 库存扣减、订单金额、支付流水、状态和通知 |
| S2 库存不足 | 不创建有效订单，不扣款，提示可理解 |
| S3 支付超时 | 客户端重试不重复扣款，最终状态可查询 |
| S4 用户取消 | 订单变取消，库存是否释放，不能再次发货 |
| S5 重复回调 | 同一支付流水幂等，订单只完成一次 |

## 七、练习与答案

### 练习 1：登录场景

**题目**：为“登录后进入首页”设计主流程和至少 4 个异常场景。

**答案**：主流程为有效账号密码登录成功；异常包括密码错误、账号锁定、验证码过期、网络超时、登录后 Token 失效。每个场景都要验证停留页面、提示、失败次数和会话状态。

### 练习 2：订单状态

**题目**：已发货订单再次取消是否允许？如何测？

**答案**：先确认需求定义；若不允许，应返回明确提示且状态不变；若允许售后取消，则应进入退款/拦截流程。测试要核对订单、库存、物流和退款记录，不能只看按钮是否隐藏。

## 八、面试高频问法

**问：场景法和流程图有什么关系？**

**答**：流程图是识别业务节点、分支和状态的依据，场景法把这些路径组合成可执行用例。没有流程图时测试人员可以根据需求补画，但必须让业务方确认，避免测试建立在错误理解上。

## 九、课后任务

绘制“注册—登录—下单—支付—退款”流程图，至少标出 3 个判断节点和 5 条场景，并为每条场景写清数据准备、状态预期、证据和清理方式。

### 课后任务参考答案

推荐场景：S1 正常注册登录下单支付；S2 注册手机号已存在；S3 登录验证码错误；S4 库存不足下单失败；S5 支付超时后重试；S6 支付成功后申请退款。判断节点包括注册是否成功、库存是否充足、支付是否成功、退款是否满足条件。

状态预期示例：库存不足不扣库存且不进入待发货；支付超时进入“支付中”或“待支付”，相同幂等键重试不能重复扣款；退款成功后订单和支付流水状态一致。证据包括订单号、请求 ID、响应、日志、数据库记录和截图；清理方式包括取消测试订单、恢复库存和删除测试账号。解析：场景法的价值在于验证跨模块状态和数据传递，而不是把流程图重新抄成几句文字。
